# 下一步迭代开发方案 V3：高校教学数据智能助手

> 文档状态：产品、技术与分阶段开发执行方案（待审核）
> 编制日期：2026-07-18
> 重要说明：本文描述的是下一版本规划，不代表相关功能已经实现。当前已实现能力以 `docs/project_feature_catalog.md` 为唯一基线。

## 1. 版本结论

V3 建议定位为：

> **高校教学数据智能助手——以智能问数为核心，打通课程教学、学生支持与教学运行的“提问—分析—定位—处理”闭环。**

V3 不以继续扩张普通教务功能为主，也不把项目做成一套大而全的教务系统。课程、作业、考勤、通知、成绩和学生支持等高校平台功能继续存在，但在本版本中主要承担两个作用：

1. 为智能问数提供可靠、可追溯、有权限边界的业务数据。
2. 承接智能问数产生的分析结果、页面定位和待确认操作。

相较上一版以“课程成绩册”为主的思路，本方案做出以下调整：

- 成绩册从 V3 主功能调整为后续增强方向。
- 智能问数从独立页面升级为平台级能力。
- 产品目标从“生成 SQL 并展示结果”升级为“问数—解释—定位—行动—治理”。
- 增加角色上下文、认证指标、业务动作草稿、质量运营和制度知识问答。
- 坚持人工确认边界，AI 不直接发布成绩、发送通知或创建高风险事项。

## 2. 当前项目判断

### 2.1 已具备的基础

当前项目已经不是单纯的 NL2SQL 演示，已形成较完整的高校教学业务与智能问数基础。

业务方面已经具备：

- 课程、作业、提交、退回、评分和成绩发布。
- 课程公告、资料、真实场次、考勤、公开/私密答疑和通知。
- 辅导员学习支持事项、跟进记录和学生预约。
- 教学任务、确定性异常、成绩提交审批和学院聚合工作台。
- 账号注册、身份审核、多工作身份、岗位任职和人员生命周期。

智能问数方面已经具备：

- 数据源路由和多轮追问。
- Schema Linking、多路检索和关系图扩展。
- SQL 生成、失败修复、只读执行和结果格式化。
- 表、字段和行级权限限制。
- 可信度评估、用户反馈、Few-shot 示例和治理队列。
- Elasticsearch、Milvus、PostgreSQL/pgvector 服务端检索模式。

质量方面，`docs/project_feature_catalog.md` 记录的最近完整基线为 **168 passed**，并已覆盖多角色越权、SQL 安全和主要业务工作流。

### 2.2 当前主要缺口

| 维度 | 当前状态 | V3 目标 |
|---|---|---|
| 智能入口 | 仍有独立问数工具感 | 在课程、首页和管理页面中直接提问 |
| 页面上下文 | 用户仍需重复说明课程、学院和时间 | 自动带入当前页面和角色上下文 |
| 回答形式 | 偏重 SQL、表格和图表 | 同时给出结论、范围、口径、证据和风险 |
| 业务承接 | 回答后缺少连续动作 | 跳转对象、应用筛选、生成操作草稿 |
| 知识范围 | 主要检索数据库结构和业务术语 | 增加受控制度文档问答 |
| 问数治理 | 已有反馈和治理队列 | 增加全局质量、失败阶段和降级运营 |
| 前端维护 | `app.js` 体量已经较大 | 新能力采用独立可复用组件 |

## 3. 产品定位与核心闭环

产品定位调整为：

> **以高校教学业务平台为载体，以可信智能问数为核心，为学生、教师、辅导员、学院和教务提供从自然语言提问到数据解释、业务定位和人工确认处理的连续体验。**

目标闭环如下：

```text
用户在业务页面提出问题
        ↓
系统自动带入角色、课程、学院、学期和页面筛选
        ↓
问题意图路由
        ↓
固定指标 / NL2SQL / 业务状态查询 / 制度知识检索
        ↓
返回结论、范围、口径、证据、风险和可信度
        ↓
定位到课程、作业、学生支持事项或教学异常
        ↓
生成页面跳转、筛选条件或业务操作草稿
        ↓
用户确认后由现有业务 API 执行
```

### 3.1 产品原则

1. **智能问数是平台级能力。** 不再局限于独立问数页面。
2. **确定性能力优先。** 简单问题优先调用认证指标或业务 API，不强制所有问题都生成 SQL。
3. **数据范围由后端决定。** 页面上下文只能缩小授权范围，不能扩大权限。
4. **回答必须可解释。** 不能只提供一句结论或一张结果表。
5. **AI 不直接执行高风险操作。** AI 只生成分析、导航和操作草稿。
6. **智能能力与基础业务隔离。** 模型或检索故障不能影响课程、作业、通知和考勤。
7. **人的业务判断优先。** AI 结果不得直接作为处罚、正式预警或成绩决定。

## 4. 角色化智能助手

| 角色 | 助手定位 | 典型问题 | 数据范围 |
|---|---|---|---|
| 学生 | 个人学习助手 | 我这周还有哪些任务？哪些课程需要优先处理？ | 本人课程、作业、考勤和已发布成绩 |
| 教师 | 课程分析助手 | 哪些学生同时存在多次缺勤和作业未交？ | 本人授课班及必要教学事实 |
| 辅导员 | 学生支持助手 | 本周有哪些学生需要复查？触发依据是什么？ | 本人所带行政班及必要学习事实 |
| 学院 | 教学质量助手 | 哪些课程完成率下降或成绩提交异常？ | 本学院课程运行和聚合质量数据 |
| 教务 | 教学运行助手 | 哪些教学异常已经逾期？ | 全校教学任务、异常和成绩提交状态 |
| 管理员 | 平台运维助手 | 最近哪些问题失败率高？检索是否降级？ | 数据源、检索、治理、审计和质量数据 |

### 4.1 页面融合位置

V3 至少在以下页面接入统一智能助手组件：

- 学生首页。
- 课程空间。
- 作业中心。
- 课程分析。
- 辅导员学生支持工作台。
- 学院教学运行工作台。
- 教务教学异常工作台。
- 管理员问数质量运营页面。

### 4.2 页面上下文

前端向智能助手传递结构化页面上下文，例如：

```json
{
  "page": "course_space",
  "teaching_class_id": 101,
  "semester": "2025-fall",
  "filters": {},
  "question": "哪些学生最近学习参与度下降？"
}
```

后端必须重新校验当前用户是否有权访问 `teaching_class_id=101`，不能直接信任前端参数。

## 5. 智能回答标准

每个回答应尽量包含以下结构：

1. 结论摘要和关键数字。
2. 服务端确认的数据范围。
3. 时间范围和当前页面上下文。
4. 使用的指标定义和统计口径。
5. 数据来源、数据更新时间和必要证据。
6. 截断、缺失、小样本、检索降级和低置信提示。
7. 默认折叠的 SQL、数据源路由和检索链路。
8. 可继续追问的问题。
9. 可执行的白名单业务动作。

示例：

> 数据库系统 1 班本周有 5 名学生未提交作业，其中 2 人同时存在两次缺勤。统计范围为本人授课班，时间范围为 7 月 11 日至 7 月 18 日。建议先查看未交名单，并生成课程提醒草稿。

回答不是只展示结果，还应提供：

- `查看未交名单`
- `打开对应作业`
- `生成课程提醒草稿`
- `查看相关支持事项`
- `导出当前权限范围内结果`
- `将该问法提交到治理队列`

## 6. V3 功能范围

### 6.1 P0：本轮必须完成

#### P0-1 统一智能问数编排器

在现有 NL2SQL 主链路前增加问题意图路由，至少识别：

- 固定指标查询。
- NL2SQL 数据查询。
- 业务状态查询。
- 制度或口径解释。
- 操作导航。
- 操作草稿生成。

简单、确定的问题优先读取现有业务聚合接口。例如“我有几份待批作业”应读取工作台数据；“不同作业的迟交率趋势”再进入分析视图或 NL2SQL。

#### P0-2 页面上下文协议

建立统一的页面上下文模型：

- 当前页面。
- 当前工作身份。
- 当前课程、学生、学院或学期。
- 当前筛选条件。
- 允许使用的业务域。
- 允许生成的业务动作。

所有上下文都必须经过后端权限校验。

#### P0-3 角色化助手场景包

至少完成以下助手：

- 学生个人学习助手。
- 教师课程分析助手。
- 辅导员学生支持助手。
- 学院教学质量助手。
- 教务教学运行助手。
- 管理员平台运维助手。

每个场景包包含：推荐问题、认证指标、允许访问的数据视图、回答模板、可用动作和禁止边界。

#### P0-4 认证指标与语义层

将高频指标从 Prompt 中抽离，形成可执行定义。

首批指标建议包括：

- 作业完成率、迟交率、未交人数、待批数。
- 出勤率、连续缺勤次数。
- 成绩提交进度和发布状态。
- 教学异常数量、逾期数量和处理时长。
- 学习支持待复查数和逾期数。
- 课程成绩分布和通过率。

每个指标保存：

- 名称与业务解释。
- 计算公式。
- 数据来源。
- 时间口径。
- 适用角色与数据范围。
- 最小样本量。
- 是否允许用于智能问数。

#### P0-5 证据化回答与业务跳转

智能助手返回结构化证据与动作：

```json
{
  "answer": "...",
  "scope": {},
  "evidence": [],
  "metric_definitions": [],
  "warnings": [],
  "suggested_actions": [
    {
      "type": "open_assignment_roster",
      "label": "查看未交名单",
      "params": {
        "assignment_id": 301,
        "status": "missing"
      }
    }
  ]
}
```

前端只能执行后端定义的白名单动作类型，不能执行模型生成的任意 URL、SQL 或 API 请求。

#### P0-6 服务端会话与结果管理

新增：

- 服务端问数会话历史。
- 按工作身份隔离的最近问题。
- 收藏问题和保存分析。
- 重命名、删除和恢复会话。
- 保存问题的默认上下文和时间范围。
- 正确、错误、口径不清、结果不完整等分类反馈。

用户切换工作身份后，旧身份的对话上下文和结果不得继续使用。

#### P0-7 智能问数质量运营面板

管理员可查看：

- 查询成功率。
- 平均响应时间和各阶段耗时。
- LLM、路由、检索、SQL 校验和执行失败率。
- 各角色高频问题。
- 低置信问题。
- 越权问题拒绝情况。
- 本地/服务端检索是否降级。
- 用户负反馈。
- 待处理治理项和知识沉淀效果。

### 6.2 P1：形成产品差异

#### P1-1 数据问答与制度知识双通道

除数据库问数外，接入受控高校制度文档，例如：

- 成绩管理办法。
- 请假与考勤规定。
- 学籍管理规定。
- 课程考核方案。
- 教学异常处理说明。

系统必须区分：

- “有多少人缺勤”——结构化数据查询。
- “连续缺勤如何处理”——制度文档检索。
- “哪些人符合关注条件，应如何处理”——数据和制度联合回答。

制度回答必须标明文件名称、发布部门、版本和有效期。没有可靠来源时，应明确说明无法确认，不能使用模型常识替代学校制度。

#### P1-2 主动洞察

角色首页生成少量、确定性的摘要：

- 教师：2 份作业即将截止，5 人未交。
- 辅导员：3 个事项今天需要复查。
- 学院：4 门课程成绩尚未提交。
- 教务：2 条教学异常超过处理期限。
- 管理员：服务端检索出现降级，低置信问题增加。

主动洞察由固定规则和认证指标产生，大模型只负责摘要表达。

#### P1-3 结果对比与持续关注

- 与上周、上月或上学期对比。
- 不同课程或学院的聚合对比。
- 保存一个问题作为持续关注指标。
- 数据更新后重新运行。
- 结果变化超过阈值时生成站内待办，不直接发送外部消息。

## 7. 高校信息平台功能的配合范围

V3 仍需完善部分高校平台能力，但只建设对智能问数融合有直接价值的内容。

### 7.1 本轮配合建设

- 完善作业、考勤、成绩和异常数据的时间、状态和来源字段。
- 为成绩提交增加基本明细快照，使助手可以回答提交完整性和缺失项。
- 通知记录增加来源追踪，能够说明由哪次分析或业务事件产生。
- 学习支持事项增加来源证据引用。
- 建立统一的学期、课程、组织、人员和指标数据字典。
- 为业务数据增加更新时间、完整性和可查询状态。

### 7.2 本轮不作为主线

- 完整课程成绩册和复杂成绩勘误。
- 在线考试、题库、自动组卷、监考和防作弊。
- 复杂排课、选课和毕业审核。
- AI 自动批改或自动决定成绩。
- 正式统一身份认证和组织主数据同步。
- 短信、邮件和企业微信正式集成。

## 8. 技术架构方案

### 8.1 目标架构

```text
业务页面 / 通用智能助手组件
              ↓
Assistant Orchestrator
              ↓
问题意图路由
      ┌───────┼────────┬──────────┐
      ↓       ↓        ↓          ↓
认证指标   NL2SQL   业务状态 API   制度文档 RAG
      └───────┼────────┴──────────┘
              ↓
权限与数据范围校验
              ↓
证据、口径、可信度与风险编排
              ↓
白名单 Action Draft
              ↓
用户确认 + 再次鉴权 + 现有业务 API
```

### 8.2 建议新增模块

```text
app/
├─ api/
│  └─ assistant.py
├─ core/
│  ├─ assistant_orchestrator.py
│  ├─ assistant_context.py
│  ├─ semantic_metrics.py
│  ├─ answer_evidence.py
│  ├─ action_drafts.py
│  └─ document_rag/
└─ static/
   └─ assistant-panel.js
```

模块职责：

| 模块 | 职责 |
|---|---|
| `assistant.py` | 统一助手、会话、收藏、反馈和动作确认 API |
| `assistant_orchestrator.py` | 意图识别、执行路径选择和结果编排 |
| `assistant_context.py` | 页面、角色和数据范围上下文 |
| `semantic_metrics.py` | 认证指标和统一口径 |
| `answer_evidence.py` | 数据来源、证据、范围、风险和引用 |
| `action_drafts.py` | 白名单动作草稿、预览、确认和过期控制 |
| `document_rag/` | 受控制度文件解析、版本、召回和引用 |
| `assistant-panel.js` | 可嵌入不同业务页面的智能助手组件 |

新增功能应使用独立模块，避免继续扩大现有大体量 `app.js` 和 `routes.py`。

### 8.3 建议数据模型

- `assistant_session`：问数会话、所属用户、工作身份和上下文。
- `assistant_turn`：问题、回答、状态和执行结果。
- `assistant_saved_query`：收藏问题、默认上下文和重跑设置。
- `assistant_action_draft`：动作类型、结构化参数、预览、确认状态和有效期。
- `metric_definition`：指标公式、口径、数据来源、适用角色和最小样本量。
- `query_execution_trace`：路由、检索、模型、校验、执行、降级和耗时信息。
- `document_knowledge_source`：制度来源、发布部门、版本、有效期和权限。
- `document_chunk`：文档切片、索引和版本关联。
- `answer_citation`：回答结论与数据证据、指标或制度来源的关联。

### 8.4 安全与权限约束

1. 页面上下文只能缩小服务端权限，不能扩大权限。
2. 智能助手不得通过前端参数绕过课程、行政班或学院范围。
3. Action Draft 必须使用枚举动作和结构化参数。
4. 动作草稿必须设置有效期和一次性确认状态。
5. 用户确认执行时必须重新鉴权。
6. 模型不得生成或执行任意写 SQL。
7. 制度知识必须记录版本、有效期和可见范围。
8. 日志不得保存作业正文、附件内容、私密辅导记录和不必要的个人数据。
9. 智能服务异常不得阻断基础业务接口。

## 9. 开发阶段与工期

完整版本建议按 4 周规划。

### 阶段 A：智能问数基础重构（4–5 天）

- 统一智能助手 API。
- 问题意图路由。
- 页面上下文和权限复核。
- 认证指标基础结构。
- 服务端会话和反馈。

验收：同一个问题在不同角色和页面中得到不同且正确的数据范围；伪造课程或学院参数被拒绝。

### 阶段 B：课程与个人学习融合（4–5 天）

- 学生首页、课程空间、作业和考勤助手。
- 教师课程分析助手。
- 回答证据、追问和业务跳转。
- 未交名单、待批作业和提醒草稿。

验收：教师在课程页面提问时不需要重复说明课程，结果不能包含其他教师课程。

### 阶段 C：教学管理融合（4–5 天）

- 辅导员、学院和教务助手。
- 学习支持、教学异常和成绩提交跳转。
- 角色首页主动洞察。

验收：辅导员只能看到本人带班必要事实；学院只能查看本学院；教务不能读取不必要的作业正文和私密记录。

### 阶段 D：知识问答与治理（4–5 天）

- 接入有限的制度文档 RAG。
- 数据与制度联合回答。
- 智能问数质量运营面板。
- 低置信、负反馈和高频失败治理。

验收：制度回答包含来源和版本；外部检索不可用时能够明确降级，不伪造制度依据。

### 阶段 E：回归与演示（3 天）

- 多角色上下文和越权测试。
- 模型故障、检索降级和空数据测试。
- 浏览器端到端测试。
- 演示数据和演示手册。
- 更新项目功能目录、API 清单、页面表、明确边界和测试基线。

### 9.1 三周压缩版本

如果开发周期只能安排 3 周：

- 保留阶段 A、B、C 的核心能力。
- 保留质量运营面板的基础指标。
- 将制度文档联合问答调整为 P1。
- 不削减页面上下文、证据化回答、业务跳转和权限测试。

## 10. 连续验收主线

建议使用以下连续场景验证 V3：

1. 教师进入课程空间，提问：“哪些学生同时存在两次缺勤和本次作业未交？”
2. 系统只分析该教师当前课程，返回名单、证据、指标口径、数据范围和更新时间。
3. 教师点击“查看未交名单”，跳转到作业页面并自动应用筛选。
4. 教师选择“生成课程提醒”，系统生成通知草稿。
5. 教师确认后发送，学生收到站内通知。
6. 辅导员工作台能够看到范围内必要学习事实，但不能读取作业正文或教师私密评语。
7. 辅导员询问：“这些学生中哪些已有开放的支持事项？”
8. 系统结合课程事实和支持事项回答，并跳转到本人待复查列表。
9. 管理员在质量面板查看本次问数的耗时、路由、检索、SQL 校验、用户反馈和降级情况。

该主线同时证明：

- 智能问数是产品核心。
- 高校教学业务平台不是空壳。
- 问数能够进入真实工作流。
- 权限和隐私边界有效。
- AI 故障不会阻断基础业务。

## 11. V3 完成标准

1. 六类主要角色拥有符合职责的智能问数入口或运营入口。
2. 页面自动传递上下文，用户不需要重复输入课程、学院和时间范围。
3. 上下文参数由后端重新校验，不能扩大权限。
4. 回答明确显示数据范围、时间、指标口径、来源、更新时间和风险。
5. 固定指标问题不强制调用大模型生成 SQL。
6. 所有业务动作先生成草稿并由用户确认。
7. 用户确认执行时再次鉴权，过期草稿不能执行。
8. 切换工作身份后，旧身份会话和结果不可继续使用。
9. 模型、Elasticsearch、Milvus、pgvector 或文档检索异常不影响基础业务。
10. 制度回答包含来源和版本，无可靠来源时明确说明无法确认。
11. 现有 168 项测试继续通过，并增加上下文、动作草稿、降级和浏览器端到端测试。
12. `docs/project_feature_catalog.md` 同步更新已实现功能、API、页面、限制、测试基线和变更记录。

## 12. 风险与应对

| 风险 | 影响 | 应对方式 |
|---|---|---|
| 问数准确率不稳定 | 错误结论影响教师和管理人员 | 认证指标优先、证据展示、低置信提示和治理反馈 |
| 页面上下文越权 | 伪造课程或学院参数扩大范围 | 后端重新计算授权范围 |
| AI 动作越界 | 模型直接发送通知或创建事项 | 白名单动作草稿、人工确认和执行前二次鉴权 |
| 制度知识过期 | 引用失效规定 | 记录版本、有效期和发布部门，过期来源不用于当前结论 |
| 前端继续膨胀 | 维护成本和回归风险增加 | 新建独立助手组件，不继续集中写入 `app.js` |
| 版本范围扩张 | V3 变成完整教务系统 | 重型成绩、考试、排课、SSO 和外部消息不纳入 P0 |
| 智能服务不稳定 | 影响业务使用 | 固定业务功能与 AI 链路隔离，支持明确降级 |

## 13. 本轮明确不做

- 在线考试、题库、自动组卷、监考和防作弊。
- AI 自动评分、自动处罚或自动形成正式学业预警。
- 复杂排课、选课、毕业审核和完整成绩勘误。
- 统一身份认证、短信和企业微信正式集成。
- 全面迁移 React/Vue 或重写整个前端。
- 允许智能助手直接执行任意写 SQL 或模型生成的网络请求。

## 14. 审核决策项

| 序号 | 决策项 | 建议结论 |
|---|---|---|
| 1 | V3 版本定位 | 批准“高校教学数据智能助手”，智能问数作为平台级核心能力 |
| 2 | P0 范围 | 批准统一编排、上下文、角色助手、指标层、证据回答、会话和质量面板 |

## 15. 建议审核结论

建议批准以下 V3 方向：

> **以角色化、上下文化、可解释、可行动的智能问数为主线，选择课程教学、学生支持和教学运行作为三个融合场景；高校平台功能只补齐支撑问数和承接动作所必需的部分。**

V3 的产品价值不再用“新增多少页面”衡量，而应使用以下结果衡量：

- 用户是否可以在当前业务页面直接提问。
- 系统是否能够自动理解当前角色和业务范围。
- 回答是否具有明确口径和可验证证据。
- 问数结果是否能够定位到真实业务对象。
- 建议动作是否安全进入人工确认流程。
- 失败问题是否能够进入治理并持续改善。

## 17. 开发执行总则

本节开始是后续开发的直接执行依据。正式开发时应严格按照任务编号顺序推进，原则上不跨阶段并行建设。前一阶段未通过门禁，不进入下一阶段。

### 17.1 固定开发流程

每个开发任务统一按照以下顺序完成：

1. **确认用户故事：** 明确角色、入口、前置条件、主流程、异常流程和禁止边界。
2. **冻结接口契约：** 先定义请求、响应、错误码、权限要求和上下文字段。
3. **设计数据变更：** 设计可重复执行的增量迁移、索引、唯一约束和回滚方案。
4. **实现服务层：** 业务规则、权限和状态校验放入服务层，路由只负责鉴权、参数校验和调用。
5. **实现 API：** API 返回结构化、可测试的数据，不把页面拼装逻辑写进后端。
6. **实现前端：** 同时完成加载、空态、错误、无权、降级、过期和成功状态。
7. **补充种子数据：** 使用确定性数据覆盖成功、失败、越权和降级场景。
8. **补充自动化测试：** 至少覆盖当前用户、同范围其他用户、跨范围用户、无权限用户和管理员边界。
9. **手工走查：** 使用真实演示账号完成页面操作，检查刷新、会话、通知、审计和跳转。
10. **更新功能目录：** 同步 `docs/project_feature_catalog.md` 的功能、API、页面、配置、限制、测试基线和变更记录。

### 17.2 单任务完成定义

一个任务只有同时满足以下条件才可以标记为完成：

- API 和页面主流程可用。
- 服务端权限校验无法通过前端绕过。
- 空态、错误态、无权态和降级态均有明确表现。
- 新增迁移可以重复执行，不会重复插入或重新授权。
- 新增测试通过，原有完整测试无回归。
- 演示数据能够稳定复现功能。
- 日志和审计不泄露作业正文、私密记录和不必要个人数据。
- `docs/project_feature_catalog.md` 已同步更新。
- 对应阶段验收用例可以从 UI 或正式 API 完整走通。

### 17.3 变更控制

- 开发过程中新增需求先进入待办池，不直接插入正在进行的任务。
- 发现安全问题时可以暂停功能开发，优先修复安全问题并补充回归测试。
- 任务范围发生实质变化时，先修改本开发方案并重新审核。
- 不以“代码已经写完”作为完成标准，必须通过阶段门禁。
- 规划中的页面、API、表和能力在真正完成前不得写入功能目录的“已实现”部分。

- 返回数据来源及刷新时间。

- 区分用户可见摘要与管理员调试详情。
- 对小样本、空结果、截断和低置信进行结构化提示。

完成条件：用户不查看 SQL 也能理解结果从哪里来、统计了什么和有哪些限制。

#### V3-2.3 白名单动作草稿

建议新增：

- `app/core/action_drafts.py`
- `assistant_action_draft` 表。

首批动作严格限制为：

- `open_assignment_roster`
- `open_course`
- `open_support_case`
- `open_teaching_issue`
- `apply_safe_filter`
- `draft_course_notification`
- `submit_governance_feedback`
- `export_current_result`

动作流程：

```text
回答生成建议动作
    ↓
服务端校验动作类型和参数
    ↓
保存短期有效草稿
    ↓
前端展示预览
    ↓
用户确认
    ↓
服务端重新鉴权
    ↓
调用现有业务 API 或安全导航
```

必测场景：

- 篡改动作类型。
- 篡改课程、学生或学院参数。
- 过期草稿。
- 重复确认。
- 切换角色后确认旧草稿。
- 通知草稿未经确认不得发送。

**阶段 V3-2 门禁：** 指标口径一致、回答证据完整、动作草稿无法越权或重复执行。

### 阶段 V3-3：角色页面融合

**目标：** 将统一助手真正接入高校业务页面，形成可演示的工作闭环。

#### V3-3.1 通用前端助手组件

建议新增：

- `app/static/assistant-panel.js`
- `app/static/assistant-panel.css`，或在现有样式体系中建立完全作用域化区域。

组件状态：

- 初始推荐问题。
- 提问中。
- 澄清中。
- 成功回答。
- 空结果。
- 低置信。
- 检索降级。
- 无权限。
- 服务异常。
- 动作草稿预览和确认。

组件不能保存或推断权限，只消费服务端返回的上下文和动作。

#### V3-3.2 学生与教师场景

学生接入：

- 学生首页。
- 课程空间。
- 作业中心。
- 本人考勤和课程分析。

教师接入：

- 教师首页。
- 课程空间。
- 作业批阅。
- 考勤管理。
- 课程分析。

首条完整链路：

> 教师在课程空间询问未交与缺勤交集 → 查看未交名单 → 生成提醒草稿 → 确认发送 → 学生收到通知。

#### V3-3.3 辅导员场景

接入：

- 辅导员首页。
- 学习支持工作台。
- 学生预约和待复查列表。

首条完整链路：

> 辅导员询问本周待复查事项 → 查看事实依据 → 定位支持个案 → 人工记录跟进。

系统不得根据模糊行为自动创建正式风险标签，也不得向辅导员返回非带班学生数据。

#### V3-3.4 学院与教务场景

学院接入：

- 课程运行。
- 教师工作量。
- 教学质量和成绩审批。

教务接入：

- 教学任务。
- 教学异常。
- 成绩发布。

首条完整链路：

> 教务询问逾期异常 → 查看异常课程 → 应用状态筛选 → 进入现有异常处理页面。

#### V3-3.5 管理员质量运营面板

新增页面或管理员工作台模块：

- 总查询数和成功率。
- P50/P95 响应时间。
- 路由、检索、模型、校验和执行失败分布。
- local/server 检索使用与降级比例。
- 低置信和负反馈问题。
- 越权问题拒绝数量。
- 高频问题和待治理项。

运营页面不展示原始私密问题正文；敏感问题应脱敏或仅展示分类摘要。

**阶段 V3-3 门禁：** 学生、教师、辅导员、学院、教务、管理员六角色完成菜单、页面、API 和字段范围回归。

### 阶段 V3-4：制度知识与混合问答

**目标：** 在结构化数据问数之外，增加带来源、版本和有效期的高校制度知识回答。

> 如果 V3 采用三周压缩版本，本阶段可以整体后移，但不得提前声称制度问答已经实现。

#### V3-4.1 制度知识源管理

建议新增：

- `document_knowledge_source`
- `document_chunk`
- `answer_citation`
- `app/core/document_rag/`

首版仅支持管理员接入经过审核的：

- Markdown/TXT 制度文本。
- 可可靠抽取文字的 PDF 或 DOCX。
- 明确的发布部门、版本、发布日期和有效期。

必须支持：

- 文件类型和大小校验。
- 文档 hash 与重复保护。
- 版本更新和停用。
- 权限范围。
- 索引失败状态。
- 引用到具体来源文档。

#### V3-4.2 数据与制度联合问答

问题分解为：

1. 数据事实查询。
2. 制度依据检索。
3. 联合回答编排。

联合回答必须明确区分：

- 系统查到的事实。
- 制度文件原意的摘要。
- 模型生成的建议。
- 需要人工判断的部分。

完成条件：没有有效制度来源时，系统明确说明无法确认，不使用模型常识伪造学校规定。

**阶段 V3-4 门禁：** 文档版本、有效期、权限、引用和无来源降级测试全部通过。

### 阶段 V3-5：质量、回归与发布准备

**目标：** 建立可重复的智能问数质量评估、浏览器验收和发布检查。

#### V3-5.1 场景评测集

新增 V3 评测集，按角色覆盖：

- 固定指标问题。
- NL2SQL 问题。
- 上下文追问。
- 模糊问题和澄清。
- 越权问题。
- 无数据问题。
- 小样本问题。
- 检索降级问题。
- 制度问题和混合问题（如已实现 V3-4）。

每条用例记录：

- 角色和上下文。
- 预期回答类型。
- 必须包含的数据范围。
- 禁止出现的表、字段和人员数据。
- 预期指标或 SQL 约束。
- 是否允许产生动作草稿。

#### V3-5.2 浏览器端到端测试

至少覆盖：

1. 教师课程问数—查看名单—提醒草稿—确认发送。
2. 学生收到通知—跳转课程—查看本人任务。
3. 辅导员问数—定位支持事项—记录跟进。
4. 教务问数—筛选异常—进入处理页面。
5. 切换角色后会话和动作草稿失效。
6. 模型或检索失败时页面显示降级态，基础业务仍可用。

#### V3-5.3 发布门禁

发布前必须完成：

- Python 编译检查。
- 完整 pytest 回归。
- 六角色产品回归。
- V3 智能问数评测。
- 浏览器端到端测试。
- local/server 检索验证。
- 数据迁移重复执行验证。
- 安全与隐私检查。
- 文档和功能目录更新。

**阶段 V3-5 门禁：** 所有 P0 验收链路可稳定复现，测试通过，文档与实现一致，才可宣布 V3 完成。

## 19. 阶段依赖关系

```text
V3-0 基线与契约
    ↓
V3-1 上下文 / 会话 / 编排器
    ↓
V3-2 指标 / 证据 / 动作草稿
    ↓
V3-3 六角色页面融合
    ↓
V3-4 制度知识与混合问答（可作为 P1 后移）
    ↓

```

不得提前执行的依赖关系：

- 未完成上下文权限校验前，不接入角色页面。
- 未完成动作草稿二次鉴权前，不开放提醒发送等操作。
- 未建立文档版本和有效期前，不开放制度知识回答。
- 未建立评测集和阶段追踪前，不以少量演示问题宣称问数质量达标。

```text
任务编号：V3-x.x
完成内容：
修改文件：
新增/修改 API：
数据迁移：
权限边界：
测试结果：
手工验收结果：
功能目录更新：
已知限制：
下一任务：
```

推荐的后续执行指令顺序：

1. `开始执行 V3-0.1`：复核当前测试和功能基线。
2. `开始执行 V3-0.2`：冻结统一助手 API 契约。
3. `开始执行 V3-0.3`：建立 V3 增量迁移基础。
4. `开始执行 V3-1.1`：实现页面上下文与权限复核。
5. 后续严格按照本文任务编号继续。

每次开始新任务前，应先检查上一任务的完成报告和阶段门禁，不从中间任务直接起步。
