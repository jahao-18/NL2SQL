# 阶段 4 实施说明：课程分析与上下文问数

## 1. 本阶段目标

阶段 4 将通用“智能问数”落到真实课程场景中，形成任课教师和学生可直接使用的课程分析工作台。实现遵循三个边界：指标口径固定且可解释、问数范围由后端强制、分析服务故障不影响作业主流程。

## 2. 已完成范围

### 2.1 固定课程指标

- 教师：作业完成率、迟交率、待批阅数、作业数，并展示各作业的应交、已交、未交、迟交率、待批阅和平均分。
- 学生：本人作业完成率、迟交率、待完成数和已发布成绩平均分，并展示本人的任务状态。
- 页面明确展示统计范围、刷新时间、数据来源和指标定义。
- 草稿作业不纳入统计；学生成绩只读取已发布的批阅记录。

### 2.2 课程上下文问数

- 常用问题使用受控模板，例如“本班各作业未交情况”“哪些作业迟交率高”“我的课程还剩哪些任务”。
- 自由问题进入现有 NL2SQL 服务，但只开放脱敏分析表。
- 教师查询必须同时包含本人 `teacher_id` 和当前 `teaching_class_id`。
- 学生查询必须同时包含本人 `student_id` 和当前 `teaching_class_id`。
- 附件、正文、评语、联系方式、帮扶记录、学生名单等问题会在进入模型前拒绝。

### 2.3 查询留痕

`analytics_query_log` 记录提问人、角色、问题、生成 SQL、课程范围、执行方式、结果行数、置信度、状态、错误和时间。日志不保存查询结果内容，也不会自动触发学习支持事件。

## 3. 数据设计

- `course_assignment_analytics`：教师可用的作业级汇总快照，不含学生身份、提交正文和附件。
- `student_task_analytics`：学生本人任务快照，不含姓名、正文、附件、评语和帮扶数据。
- `analytics_query_log`：课程问数审计记录。

分析快照由事务数据刷新生成，是只服务查询的派生数据，不替代作业、提交和批阅业务表。

## 4. API

- `GET /api/teaching/analytics/contexts`：当前账号可分析课程。
- `GET /api/teaching/analytics/summary?teaching_class_id=...`：固定指标与明细。
- `POST /api/teaching/analytics/ask`：课程上下文问数。
- `GET /api/teaching/analytics/history?teaching_class_id=...`：本人近期查询记录。
- `PATCH /api/teaching/analytics/history/{log_id}/feedback`：记录本人对结果的“有帮助/需改进”反馈。

## 5. 开发与验收流程

1. 先由作业、选课、提交和成绩发布表刷新脱敏快照。
2. 在服务层校验教师授课关系或学生选课关系，不能依赖前端传入身份。
3. 固定指标直接读取受限快照，并返回指标口径和更新时间。
4. 优先匹配常用问题模板；未匹配的问题才进入 NL2SQL。
5. NL2SQL 只接收分析表 Schema，并在 SQL 校验阶段强制身份和课程谓词。
6. 无论成功或失败都写查询留痕，失败不写入学习支持事件。
7. 回归作业提交、修改、批阅、成绩发布和学习支持流程，确认分析模块没有形成反向依赖。

## 6. 阶段验收点

- `tea_li` 访问 `tea_zhou` 的开课班返回 403。
- 学生汇总结果的每一行均固定为本人 `student_id`。
- 缺少 `teaching_class_id`、教师本人或学生本人谓词的分析 SQL 被校验器拒绝。
- 学生看不到未发布成绩；教师分析结果不返回学生身份。
- NL2SQL 返回错误时，作业列表、提交和批阅接口仍正常工作。
- 前端可切换课程、刷新指标、执行模板或自由问题，并查看本人查询历史。

## 7. 后续阶段入口

阶段 5 可在本阶段的可信指标基础上增加通知中心、课程消息和教师批量提醒。任何提醒都应由明确业务规则和人工操作触发，不能直接由低置信度问数结果触发。
