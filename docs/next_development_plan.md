# 高校教学运行与智能分析平台：下一步开发方案

## 1. 结论

当前项目的技术底座并不差：已具备 FastAPI、教学数据模型、NL2SQL、Schema 治理和基础 RBAC。但产品仍停留在“对一套模拟历史数据做查询和展示”的层面，缺少真实高校教学平台最重要的部分：**按人、按课、按时间发生的业务动作和处理闭环**。

建议将产品定位由“教学数据智能问数平台”调整为：

> **面向高校日常教学运行的课程学习与教学协同平台，以角色权限和过程数据为基础，以智能问数和风险研判为辅助。**

产品主线应为“学生学习 - 教师教学 - 辅导员帮扶 - 教学管理”四条闭环，NL2SQL 降为各工作台内的分析助手，而非首页唯一主功能。

### 1.1 进一步收敛：首版只解决一个真实问题

不要把项目做成“简化版学习通 + 简化版教务系统 + 简化版学生工作系统”。这样的范围无法在课程项目周期内做深，也无法证明实际价值。

首版应聚焦为：

> **课程作业全过程与学习困难早发现、早反馈、早帮扶。**

它服务的真实问题是：学生不知道有哪些任务临期或自己的学习状态；教师需要靠聊天群和表格催交、收作业、登记成绩；辅导员往往在挂科或试读警告后才发现问题，缺少可追踪的课程参与信号。平台让“作业未交/迟交 - 教师反馈 - 学生补交 - 辅导员跟进”成为可追踪的闭环，而不是单一的风险排行榜。

这一选择既回应了老师提出的“上传作业”等实际场景，也能自然复用项目已有的 `assignment`、`assignment_submission`、`attendance`、`learning_activity` 与 `academic_warning` 数据。上海大学已公开开展以预警、辅导员结对、朋辈小组和期中摸底为内容的学业帮扶，并强调以数据支持持续改进，说明“预警后的支持过程”比展示预警数字更有现实意义。[上海大学：本科生学业帮扶专题工作会议](https://www.shu.edu.cn/info/1056/320305.htm)

### 1.2 价值假设与成功标准

| 使用者 | 当前低效做法 | 平台提供的直接价值 | 首版可验证指标 |
| --- | --- | --- | --- |
| 学生 | 从群消息和多个平台翻找截止日期，无法确认提交是否成功 | 一个待办页、提交回执、退回/补交提醒、个人学习建议 | 每次提交均产生回执；临期任务能在首页显示 |
| 任课教师 | 用群文件收作业、Excel 登记分数、人工筛未交名单 | 发布、收取、批阅、退回、成绩发布和本班完成率在一个课程页完成 | 可在 3 分钟内定位未交/待批作业；成绩不向未发布学生泄露 |
| 辅导员/班导师 | 期末或处分节点才获知学习困难，记录分散 | 对所带班级接收经规则触发的待跟进事项，记录帮扶和复查 | 每个预警都有依据、责任人、状态和下一次复查日期 |
| 学院/教务 | 只看结果性挂科率，难以判断过程问题 | 仅看聚合的作业完成和课程运行趋势，定位需要支持的课程 | 可按学院/课程查看聚合趋势，默认不暴露学生隐私 |

**首版成功不以“页面数量”衡量，而以三条链路能否完整走通衡量：**学生成功交作业、教师成功形成反馈、辅导员能据可解释的信号完成一次帮扶记录。

### 1.3 首版范围边界

| 本次必须做（MVP） | 后续再做 | 首版明确不做 |
| --- | --- | --- |
| 多账号和数据范围、课程页、作业发布/提交/批阅/补交、通知、基础成绩发布、辅导员帮扶待办、课程完成率、审计与越权测试 | 资源章节、讨论、课堂考勤、题库测验、成绩册权重、学院聚合分析、上下文问数 | 排课选课、正式考试、防作弊、人脸签到、直播、复杂 AI 判作业、心理风险推断、对接真实学校生产数据 |

这条边界尤其重要：首版不采集与课程任务无关的行为数据，不依据模糊行为给学生贴风险标签，也不以 AI 自动决定成绩或预警结论。

## 2. 调研依据与可借鉴点

### 上海大学

- 上海大学本科生院公开的教务系统业务包含选课、教学任务、点名册、教学计划、排课、课程大纲、学籍、考试、成绩录入、毕业审核和试读警告；另一入口还覆盖评教、毕业论文、跨学科联合大作业、实习实践等。这说明高校系统通常按业务域拆分，而不是让所有角色进入同一个数据大屏。[上海大学本科生院：教务管理系统](https://bksy.shu.edu.cn/index/jxgl1/jwglxt.htm)
- 上海大学公开的混合教学安排要求学生完成通知关注、作业、讨论、阶段测验和线上考核，并把过程成绩、线上成绩、线下成绩纳入总评。这是本项目最适合复现的“课程运行闭环”。[上海大学：在线与课内混合教学安排](https://www.xk.shu.edu.cn/info/1021/1291.htm)

### 主流高校教学平台

- 中国大学 MOOC 的学校云将课程资源、校内课程运行、课堂活动、AI 助教和学情数据连接在同一教学流程中，强调“数据反馈 - 持续改进”，而不是孤立的报表查询。[中国大学 MOOC 智慧教学产品体系](https://smartedu.icourse163.org/)
- 高校 MOOC 平台的公开采购需求通常要求：课程任务点、资源分发、作业发布/提交/批阅、题库与测验、通知讨论、成绩册、学习过程统计等能力；作业应支持附件、提交状态、评分公开策略，教师基于本班数据开展教学调整。[广东石油化工学院：网络教学管理平台功能说明](https://www.gdupt.edu.cn/wxzx/info/1343/4467.htm)
- Sakai 的公开高校实例支持课程内容组织、分组、面向特定对象的资源分发、作业、测验、讨论、花名册、日程和站点统计，适合借鉴“课程站点是业务边界”的设计。[江苏大学 Sakai](https://sakai.ujs.edu.cn/)

## 3. 当前系统与目标系统的差距

| 维度 | 当前状态 | 目标状态 |
| --- | --- | --- |
| 产品主场景 | 仪表盘与自然语言查数 | 课程运行、作业、课堂互动、学习支持与教学管理 |
| 账号 | 每角色 1 个固定演示账号 | 多个实名业务账号，账号绑定学生/教师/辅导员及组织范围 |
| 权限 | 角色 + 部分表/字段限制 | 功能权限 + 数据范围 + 课程成员关系 + 操作审计 |
| 作业 | 仅有作业及提交结果的静态表 | 教师发布、学生提交/补交、教师批阅、退回、成绩回写的全流程 |
| 学业预警 | 被作为通用数据卡片展示 | 仅对学生本人、辅导员/班导师和有授权的学生工作管理人员开放，并形成干预记录 |
| 教师工作台 | 查询本人班级历史数据 | 班级花名册、待批作业、考勤、公告、成绩册、学习进度和课程内分析 |
| 智能问数 | 平台核心入口 | 结合当前课程/班级/权限的解释、统计与待办辅助 |

## 4. 用户、数据范围与职责

### 4.1 角色设计

| 角色 | 主要工作台 | 可看数据范围 | 不应拥有的权限 |
| --- | --- | --- | --- |
| 学生 | 我的课程、待办、作业、成绩、个人预警 | 本人及本人选课班 | 同学名单、全班成绩、他人预警 |
| 任课教师 | 我的开课班、作业批阅、考勤、成绩册、课程学情 | 本人任课班及其选课学生 | 非本人课程、学生跨课程信息、学业预警处理 |
| 助教 | 被授权课程的资源、答疑、批阅协作 | 被授予的课程和班级 | 最终成绩发布、敏感学生档案 |
| 辅导员/班导师 | 所带班级学生画像、预警、干预、通知 | 所带行政班学生 | 其他班级、课程原始评教、全校分析 |
| 学院教学秘书/负责人 | 本学院开课运行、课程质量、异常汇总 | 本学院聚合数据；按授权查看明细 | 其他学院明细、学生工作干预记录 |
| 教务处 | 排课、选课、成绩、考试、毕业审核、校级质量分析 | 全校教务业务范围 | 辅导员私密谈话内容、原始匿名评教文本 |
| 系统管理员 | 账号、组织、权限、审计、数据治理 | 系统管理元数据 | 默认不直接浏览教学明细，采用最小授权 |

**关键原则：** 任课教师应当能查看自己课程的花名册、作业和考勤；学生只能查看个人信息；预警不放进教师默认页面。辅导员获得的是“需要开展帮扶的名单和处理任务”，而非泛化的全校风险排行榜。

### 4.2 账号与身份实现

1. 保留演示模式，但将 `DEMO_USERS` 改为至少 18 个账户：6 名学生、4 名教师、2 名助教、3 名辅导员、2 名学院人员、1 名教务人员；每个账户关联真实存在的 `student.id`、`teacher.id` 或新增的 `counselor.id`。
2. 新增 `user`、`role`、`user_role`、`counselor`、`counselor_class_group`；密码使用 `bcrypt/argon2` 哈希，登录令牌含用户 ID、角色及会话过期时间。
3. 所有业务 API 从认证上下文推导 `student_id`、`teacher_id`、`class_id`、`college_id`，禁止前端传入可篡改的范围 ID。
4. 在查询、文件下载、批阅、成绩发布、干预记录等写操作均写入审计日志。

## 5. 优先建设的业务闭环

### 闭环 A：作业与成绩（第一优先级）

这是最直观、最适合答辩演示且能持续产生真实过程数据的场景。

1. 教师进入“我的开课班”，发布作业：标题、说明、附件、类型、发布时间、截止时间、满分、是否允许补交、评分标准。
2. 学生在“我的待办”看到即将截止任务，上传文件或填写文本；支持草稿、重新提交、逾期标记和提交回执。
3. 教师按“未批阅/已逾期/需退回”筛选，在线查看附件、给分、写评语、退回重交；可一次发布成绩。
4. 学生收到成绩和评语通知，课程成绩册同步汇总作业权重。
5. 课程维度自动产生“未提交率、迟交率、得分分布、题目失分点”分析，供教师改进教学。

**演示脚本：** 学生张同学提交“数据库系统第 3 次作业” -> 教师李老师批阅并退回一份不合格作业 -> 学生补交 -> 教师发布成绩 -> 课程学情显示作业完成率变化。

### 闭环 B：课程站点与课堂互动（第二优先级）

1. 课程站点包含公告、教学大纲、章节资源、任务清单、作业、测验、讨论和成绩册。
2. 教师发布公告、上传资源、设置章节任务；学生查看进度、下载资料、提问和参与讨论。
3. 教师发起一次课堂考勤或随堂测验；学生签到/答题；教师即时查看缺勤和答题统计。
4. 将学习行为限定为课程教学必要数据，清晰说明采集用途和保留期限，避免无目的监控。

### 闭环 C：学业预警与帮扶（第三优先级）

1. 预警由规则引擎或人工创建：例如多门必修不及格、连续缺勤、长期未提交任务；每条预警必须展示命中依据、生成时间、责任人和状态。
2. 学生只能看见自己的预警、建议和可预约的帮扶事项；不显示风险评分算法细节或他人信息。
3. 辅导员/班导师在“学生帮扶”工作台查看本人所带班级待处理预警，记录联系、谈话、转介、学生反馈、复查日期和解除结论。
4. 教师只可在课程范围收到“需关注的学习参与情况”提示，不直接接收学生学业预警档案。

## 6. 数据模型演进

在现有 `student`、`teacher`、`teaching_class`、`enrollment`、`assignment`、`assignment_submission` 基础上迭代，避免另起一套平行数据。

| 模块 | 新增/调整表 | 关键字段 |
| --- | --- | --- |
| 身份组织 | `user`、`role`、`user_role`、`counselor`、`counselor_class_group` | 外部身份号、关联对象、有效期、组织范围 |
| 课程站点 | `course_site`、`course_module`、`course_resource`、`learning_progress` | 开课班、章节、资源类型、可见时间、完成状态 |
| 作业 | 扩展 `assignment`；新增 `submission_file`、`submission_version`、`grading_rubric`、`grading_record` | 发布/截止/补交、内容、版本、附件、评分项、评语、发布状态 |
| 互动 | `announcement`、`discussion_topic`、`discussion_post`、`attendance_session`、`quiz`、`quiz_attempt` | 课程成员关系、发布时间、状态、参与记录 |
| 成绩 | `grade_item`、`gradebook`、`grade_publish_log` | 成绩项权重、草稿/发布、成绩来源、发布批次 |
| 预警帮扶 | 扩展 `academic_warning`；新增 `warning_rule`、`intervention_case`、`intervention_log` | 触发依据、责任辅导员、处置状态、随访日期、隐私级别 |
| 平台能力 | `notification`、`file_asset`、`audit_log` | 接收人、已读、文件存储键、操作者、前后值 |

数据库迁移应使用 Alembic；开发阶段可继续 SQLite，最终展示环境建议 PostgreSQL。文件只保存对象存储键和元数据，下载 API 必须再次校验课程成员关系。

## 7. 页面与导航重构

登录后不展示“角色切换”，而是展示当前人的工作台。建议导航按角色动态生成：

- 学生：`首页待办`、`我的课程`、`作业与测验`、`成绩与学分`、`学习支持`、`消息`
- 教师：`教学首页`、`我的开课班`、`作业批阅`、`考勤与互动`、`成绩册`、`课程学情`
- 辅导员：`学生帮扶`、`预警待办`、`班级概览`、`干预记录`、`通知`
- 教务/学院：`教学运行`、`开课与选课`、`成绩与考试`、`质量分析`、`课程建设`
- 管理员：`组织与账号`、`角色授权`、`数据接入`、`审计与治理`

现有的“数据维护、Schema 画像、治理队列、召回调试”等能力移动到管理员或开发运维入口，不占师生工作台。智能问数以“分析此班作业未交情况”“解释我的成绩构成”“本学院哪些课程需关注”等上下文按钮进入，并自动继承当前范围。

## 8. 分阶段路线图

### 第 0 阶段：产品收敛与数据重置（3-5 天）

- 确定上述角色与权限矩阵，删除不合理的教师预警卡片和全角色可见的管理入口。
- 建立多账号演示数据及“课程 - 教师 - 学生 - 辅导员”关系；选择 2 门课程、2 个行政班构造完整可演示链路。
- 输出接口契约、页面原型、状态机和验收脚本，再开始实现。

**验收：** 任意学生、教师、辅导员登录后均只能看到与自己关联的课程/班级/事项；越权 URL、API、下载均被拒绝。

### 第 1 阶段：作业闭环 MVP（2 周）

- 后端：身份映射、课程成员校验、作业 CRUD、提交版本、附件、批阅、成绩发布、通知、审计。
- 前端：学生待办和提交页、教师课程页和批阅队列、基础成绩册。
- 数据：为 2 门课程生成已发布、待提交、逾期、退回、已评分的完整样本。
- 测试：权限矩阵、截止时间、重复提交、文件访问、成绩发布前后可见性。

**验收：** 5 分钟内完成“发布 - 提交 - 批阅 - 补交 - 发布成绩”的跨角色演示。

### 第 2 阶段：课程运行与学情（2 周）

- 课程公告、资源、章节任务、考勤、讨论；按课程展示完成率与异常学生。
- 将现有 `learning_activity` 改为可追溯的学习事件，而非无来源的随机统计。
- 将 NL2SQL 嵌入教师/学院分析页，默认附带当前课程、学期、组织范围。

**验收：** 教师能从一个开课班完成“发布资料 - 发通知 - 发起考勤 - 查看完成情况 - 查询本班分析”。

### 第 3 阶段：辅导员帮扶闭环（1-2 周）

- 辅导员、带班关系、预警规则解释、干预工单和随访记录。
- 实现最小预警规则：连续 2 次作业未提交、缺勤达到阈值、必修课不及格；支持人工关闭且保留理由。
- 增加学生端“我的学习支持”和辅导员端“待处理事项”。

**验收：** 预警只进入对应学生和对应辅导员的队列；教师不会在默认工作台看到完整预警档案。

### 第 4 阶段：教学管理、质量分析与治理（持续迭代）

- 对接/模拟教务的开课、选课、成绩、考试数据；学院与教务只看聚合指标，需要明细时走授权。
- 完善数据字典、指标口径、导出脱敏、审计检索和异常告警。
- 逐步引入课程知识库/RAG、作业反馈辅助、问数结果引用口径，但不让 AI 直接执行高风险写操作。

## 9. 技术实施建议

1. **分层：** 在当前 FastAPI 中新增 `app/api/teaching/`、`app/services/`、`app/repositories/`；将“教学业务写操作”与现有“NL2SQL 分析”分离。避免继续在单个 `routes.py` 堆叠接口。
2. **授权：** 从当前按表名限制，升级为 `can(action, resource, scope)`；每个查询必须先取得可访问的 `teaching_class_id` / `student_id` 集合，再执行数据操作。
3. **状态机：** 作业 `draft -> published -> closed -> archived`；提交 `draft -> submitted -> returned -> resubmitted -> graded`；预警 `open -> contacted -> tracking -> resolved/closed`。状态迁移在服务层校验。
4. **文件：** 首版可使用本地受控目录，接口采用随机对象键；正式部署切换 MinIO/S3。绝不可用原文件名直接拼接下载路径。
5. **数据：** 现有随机种子数据保留给问数测试，但新增一组手工设计的“演示课程数据”，保证每个异常、提交和干预都有可解释的业务原因。
6. **AI 边界：** AI 可生成统计解释、作业反馈建议、通知草稿和风险摘要；发布成绩、修改预警结论、发送通知必须由有权限用户确认并留痕。

## 10. 答辩展示重点

不要再演示“老师询问全校预警数量”。建议演示一条连续主线：

1. 学生用自己的账号进入课程，看到待提交作业并上传。
2. 任课教师登录后只看到本人课程的花名册和待批作业，完成批阅、退回和成绩发布。
3. 辅导员登录后仅看到所带班级的“连续未交作业”帮扶事项，记录联系与复查。
4. 学院人员查看本学院课程运行的聚合指标；智能助手解释“哪些课程作业逾期率较高及原因”。
5. 展示越权拦截：学生访问同学作业、教师访问非本人课程、辅导员访问其他班级，均无法取得数据。

这条主线能同时回答“功能是否真实”“角色是否合理”“数据是否有意义”“NL2SQL 有什么价值”四个问题。

## 11. 后续开发执行流程

本节是后续实现的唯一执行顺序。每个阶段未通过验收不得进入下一阶段；新增需求先进入待办池，不打断正在进行的阶段。

### 11.1 阶段 0：需求冻结与演示数据设计

**目标：** 先确定要服务的人、发生什么事、谁能看到什么，再改代码。

| 步骤 | 具体工作 | 产出物 | 完成定义 |
| --- | --- | --- | --- |
| 0.1 | 冻结 MVP 的三种角色：学生、任课教师、辅导员；学院/教务仅保留第二期占位 | 角色权限矩阵 | 每个菜单、接口、表字段都能标明其角色和数据范围 |
| 0.2 | 选择 2 个开课班、6 名学生、2 名教师、1 名辅导员，人工编写有因果关系的演示事件 | 演示数据说明 | 至少包含按时提交、迟交、未交、退回重交、已评分、待帮扶六种状态 |
| 0.3 | 写出三条用户故事和验收场景 | `docs/mvp_acceptance_cases.md` | 产品负责人可不看代码复述完整业务流程 |
| 0.4 | 画出作业、提交、预警的状态机和权限表 | `docs/mvp_state_machine.md` | 不存在未定义的状态迁移或跨角色操作 |
| 0.5 | 确定隐私规则：课程花名册只给任课团队；帮扶记录只给对应辅导员；管理员不默认查看业务明细 | 数据分级表 | 每个敏感字段拥有访问目的、访问角色和保留规则 |

**阶段 0 的强制决策：** “预警”在首版命名为“学习支持待办”或“需关注事项”，页面先展示事实依据，例如“本课程连续两次作业未提交”，而不是展示不可解释的“风险分 82”。正式学业警告仍由教务规则和人工确认产生，不能被课程项目自动替代。

### 11.2 阶段 1：底座改造与访问控制

**目标：** 先让“谁能访问哪门课程、谁能查看哪份作业”不可绕过。

1. 新建迁移机制并为现有 SQLite 数据库建立可重复执行的迁移脚本；禁止通过手工修改线上数据库结构。
2. 将 `DEMO_USERS` 替换为可配置的演示账户集合，新增用户与学生/教师/辅导员实体的关联。
3. 在 `app/core/business_domains.py` 中保留分析域权限，但新增业务授权层；业务授权以课程成员关系、行政班带班关系为准，而不是仅按数据表白名单。
4. 新增 `require_course_member`、`require_teacher_of_class`、`require_counselor_of_student` 等服务层校验；所有读写接口调用它们。
5. 将当前教师角色对 `academic_warning` 的直接访问从默认工作台移除；教师只看到本课程客观的未交、迟交、缺勤聚合信息。
6. 将演示密码迁移为哈希存储；令牌携带过期时间，登出使会话失效。

**建议文件落点：**

| 位置 | 改动 |
| --- | --- |
| `app/models/` | 业务请求/响应模型和领域对象 |
| `app/core/business_domains.py` | 保留 NL2SQL 的分析权限，去除其承担业务访问控制的职责 |
| `app/core/authorization.py`（新增） | 课程成员、教师、辅导员范围校验 |
| `app/api/teaching/`（新增） | 课程、作业、提交、帮扶 API；不继续膨胀 `app/api/routes.py` |
| `scripts/seed_teaching_db.py` | 添加确定性的 MVP 演示账户与业务事件种子 |
| `tests/` | 按角色和资源编写越权回归测试 |

**验收用例：** 学生 A 请求学生 B 的提交详情返回 403；教师 A 请求教师 B 的课程返回 403；辅导员 A 请求非带班学生的帮扶记录返回 403；所有失败操作均不返回对象存在与否的敏感细节。

### 11.3 阶段 2：作业闭环实现

**目标：** 完成最小但完整的“发布 - 提交 - 批阅 - 补交 - 发布”流程。

按以下顺序实现，每完成一个子项即补齐 API 测试、界面状态和审计记录：

1. **教师发布：** 草稿与发布状态、标题、说明、截止时间、补交开关、满分、附件；只有任课教师可发布到自己的开课班。
2. **学生待办：** 基于本人选课记录计算待开始、进行中、临期、已逾期、已提交、被退回；首页只显示本人任务。
3. **学生提交：** 支持文本和受控文件附件，产生提交版本和服务端时间戳；截止后根据补交策略标记迟交，不能由客户端伪造时间。
4. **教师批阅：** 列出本班待批、已交、未交、迟交；支持评分、评语、退回重交和批量发布；批阅者身份、时间和前后状态写审计。
5. **学生反馈：** 成绩发布前学生只看到“已提交/批阅中”，发布后才能查看得分与评语；退回后学生可再次提交。
6. **通知：** 发布作业、即将截止、被退回、成绩发布各产生站内通知；首版不接入短信、邮件或微信。

**完成定义：** 用两个独立浏览器会话，按学生 - 教师 - 学生顺序可完整走通流程；刷新页面后状态不丢失；不依赖手工改数据库来演示任何一步。

### 11.4 阶段 3：学习支持待办与辅导员闭环

**目标：** 用可解释、最小必要的数据辅助人开展帮扶，不把系统做成自动处罚工具。

1. 首版仅配置三条透明规则：同一课程连续两次未提交、同一课程累计两次迟交、某门课程连续两次缺勤。规则命中仅创建“待确认事项”。
2. 系统将事项路由给对应行政班辅导员；若没有带班关系，进入管理员待分配队列，不允许默认广播。
3. 辅导员查看“事实依据 - 学生基本班级信息 - 建议动作”，填写联系记录、学生反馈、后续计划和复查日期。
4. 学生端只显示本人可见的支持建议、待完成任务和预约/联系入口，不显示辅导员内部工作记录。
5. 辅导员可将事项标为已联系、跟进中、已改善、关闭；关闭必须填写理由。系统只在后续事件满足条件时更新状态，不自动删除历史记录。

**验收用例：** 连续未交的学生会产生一条事项；完成补交后辅导员仍能看见历史与复查结果；同班其他学生无法得知该事项；教师能看到“未交人数”但不能查看辅导员记录。

### 11.5 阶段 4：把分析和 NL2SQL 接回业务

**目标：** 让原项目的优势解决当前工作中的具体问题，而不是替代业务流程。

1. 先实现固定口径卡片：本班作业完成率、迟交率、待批数、按作业的得分分布；每张卡片显示时间范围、数据来源和计算口径。
2. 再提供上下文问题模板，例如“本班本次作业未交情况”“哪些作业迟交率高”“我的课程还剩哪些任务”；由页面自动注入当前课程、当前用户和时间范围。
3. NL2SQL 仅访问已授权、已脱敏的分析视图，而非直接查询作业正文、学生文件、帮扶记录或个人联系方式。
4. 对每个问数结果保留问题、生成 SQL、时间、范围和用户反馈；低置信结果不作为预警触发依据。

**验收用例：** 教师在课程 A 中提问时结果不含课程 B；学生提问时 SQL 结果被限制为本人；NL2SQL 故障不影响作业提交与批阅。

### 11.6 每个开发迭代的固定流程

后续每次开发按以下流程执行，避免功能做完才发现不符合场景：

1. **确认故事：** 从本方案选择一条用户故事，写清角色、前置条件、主流程、异常流程、权限和验收条件。
2. **先改数据与接口：** 设计迁移、状态机、Pydantic 模型和 API 契约；评审权限校验点，再开始页面开发。
3. **实现服务层：** 将规则放在服务层，路由只做鉴权、参数校验和调用；禁止将权限判断散落在前端。
4. **实现页面状态：** 同时实现空态、加载、无权限、截止、退回、发布前/后等状态，不只做成功页面。
5. **种子数据与测试：** 为该功能加入确定性样本和 API/权限测试；测试至少覆盖本人、同课程成员、跨课程用户、管理员四种身份。
6. **手工走查：** 使用两个或三个账号按验收故事操作，确认数据持久化、刷新、通知、审计及越权拦截。
7. **更新文档：** 记录 API、数据字典、权限矩阵、演示步骤和已知限制；只有文档、测试、界面同步完成才关闭任务。

### 11.7 发布前质量门禁

| 检查项 | 必须满足的条件 |
| --- | --- |
| 功能完整性 | 三条主链路均可从 UI 走通，不依赖数据库手改 |
| 权限安全 | 所有跨学生、跨课程、跨辅导员范围的 API 自动化测试通过 |
| 数据可信 | 演示数据可解释且前后一致；看板指标可追溯到提交、批阅、考勤事件 |
| 隐私边界 | 不在教师页面呈现学生工作记录；不在学生页面呈现他人数据；日志不写附件正文和敏感评语 |
| 稳定性 | 文件大小、类型、路径均受限；重复提交、网络刷新、重复点击不产生脏数据 |
| 可演示性 | 新同学按演示脚本 10 分钟内可完成三角色演示；准备失败场景和恢复步骤 |
