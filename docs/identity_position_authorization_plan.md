# 组织岗位授权与多角色账号开发方案

> 修订说明：本版基于当前 6 个学院仅有 1 个学院负责人账号、教务与管理员均为单账号、辅导员覆盖不足的实际数据审计进行了组织模型升级。核心模型由“给账号绑定角色”调整为“组织单元＋岗位编制＋自然人任职＋组织审核队列”。

## 1. 方案定位

本方案作为阶段 C 之前的 **阶段 B.6：组织岗位授权与多角色账号**。

阶段 B.5 已经解决学生和普通教职工自主注册、身份匹配及组织审核问题，但辅导员、学院负责人、教务处老师和平台管理员仍依赖初始化代码或数据库维护。本阶段需要把这些高权限身份转化为可操作、可审核、可追溯的正式产品能力。

本阶段目标不是开放管理角色注册，而是建立以下完整链路：

```text
创建登录账号
→ 验证校内自然人身份
→ 获得基础身份
→ 根据岗位任命获得一个或多个业务角色
→ 登录后选择或切换当前工作身份
→ 后端根据当前身份计算菜单和数据范围
→ 岗位调整、到期或撤销后立即失效
```

## 2. 当前不足

### 2.1 教职工目录等同于教师目录

当前“教职工注册”只匹配 `teacher` 表。这会造成：

- 不承担授课任务的行政人员无法注册。
- 辅导员必须被错误地建模为教师或使用独立演示账号。
- 教务处老师、学院负责人和管理员缺少统一的自然人身份来源。

### 2.2 账号只有一个实际生效角色

`app_user.role` 只能表达一个当前角色。虽然系统已有 `user_role` 表，但认证、Token、导航和数据范围仍读取 `app_user.role`，没有真正支持多角色。

这会导致一名教师成为辅导员后只能覆盖原角色，无法同时使用教师工作台和辅导员工作台。

### 2.3 高权限岗位没有正式授权流程

辅导员、学院负责人、教务处老师和管理员目前只能通过初始化脚本或直接修改数据库产生，缺少：

- 授权申请或岗位任命入口。
- 授权范围选择。
- 授权人权限检查。
- 生效时间和失效时间。
- 撤销、停用、交接和审计记录。

### 2.4 角色和数据范围耦合在账号字段中

当前 `student_id`、`teacher_id`、`counselor_id` 和 `college_id` 直接挂在 `app_user` 上，不适合表达：

- 一个用户拥有多个身份。
- 一名辅导员负责多个行政班。
- 一名学院负责人负责多个学院或临时代管学院。
- 同一个岗位具有不同有效期。

### 2.5 管理员缺少安全保护

当前没有防止以下危险操作：

- 停用最后一个管理员。
- 管理员直接给自己提升权限。
- 无二次确认地批量授予管理员。
- 管理员授权没有原因和审计证据。

### 2.6 组织岗位覆盖严重不完整

当前教学数据库实际包含 6 个学院：计算机学院、数学与统计学院、经济管理学院、人文与艺术学院、智能工程学院和健康科学学院，但只有一个名为 `college` 的学院负责人账号，并且只绑定计算机学院。

当前组织账号覆盖情况：

| 项目 | 当前数量 | 主要问题 |
| --- | ---: | --- |
| 学院 | 6 | 只有计算机学院存在负责人账号 |
| 学院负责人账号 | 1 | 其他 5 个学院的教师申请无法进入本学院审核队列 |
| 教务处账号 | 1 | 所有无负责人申请都会集中到单一账号 |
| 管理员账号 | 1 | 存在单点故障，也无法验证“最后一个管理员保护” |
| 辅导员账号 | 2 | 均属于计算机学院，其他学院和大量行政班没有覆盖 |
| 教师 | 242 | 与管理岗位账号数量不匹配 |
| 学生 | 约 8,932 | 大量注册申请只能回退到教务处理 |

当前注册流程在找不到辅导员时回退给教务、找不到学院负责人时回退给管理员。这只能作为异常兜底，不能成为常态，否则教务和管理员会成为全校账号审核中心。

### 2.7 使用角色名称作为共享账号

`admin`、`jwc`、`college`、`teacher` 和 `student` 等账号更像角色名称，而不是可追责的自然人账号。共享或泛化账号会造成：

- 无法确认具体操作人。
- 人员离职后无法单独撤销权限。
- 密码可能在多人之间传播。
- 审计日志只能记录角色，不能记录责任人。
- 无法支持一人多岗和岗位交接。

正式环境必须使用学号或工号登录，并绑定真实自然人。现有泛化账号只能作为明确标记的演示兼容账号，不能作为正式组织岗位方案。

### 2.8 缺少完整账号生命周期

当前方案还需要补齐：

- 忘记密码和受审计的密码重置。
- 连续登录失败锁定、解锁和风险提醒。
- 学生毕业、休学、复学和退学后的账号状态。
- 教职工入职、调动、借调和离职后的权限变化。
- 学院合并、更名和行政班调整后的范围迁移。
- 账号长期未使用、异常登录和高权限操作复核。

## 3. 核心产品原则

### 3.1 注册、自然人身份和岗位权限分离

- 注册解决“如何登录”。
- 校内身份解决“这个账号对应谁”。
- 岗位授权解决“这个人现在承担什么职责”。
- 数据范围解决“这个岗位可以管理哪些对象”。

任何用户都不能在注册页面直接选择辅导员、学院负责人、教务或管理员角色。

### 3.2 角色可以有多个，但每个会话只有一个当前角色

一个账号可以同时拥有任课教师和辅导员角色，但一次会话只以一个角色工作。不同角色的菜单、首页和数据范围不能合并。

### 3.3 权限来源必须可解释

每一个生效权限都必须能回答：

- 谁授予的。
- 为什么授予。
- 管理范围是什么。
- 什么时候开始生效。
- 什么时候到期或被撤销。

### 3.4 范围来自组织关系，不由用户自由填写

- 任课教师范围来自开课班任课关系。
- 辅导员范围来自行政班分配。
- 学院负责人范围来自学院岗位任命。
- 教务处范围来自教务岗位授权。
- 管理员范围固定为平台运维，不自动获得教学隐私明细。

### 3.5 岗位属于组织，不属于某个固定账号

系统不能预先创建一个永久的 `college` 账号代表全部学院。正确关系是：

```text
计算机学院
└─ 学院负责人岗位
   └─ 当前任职人：工号 T1001 李雨桐

数学与统计学院
└─ 学院负责人岗位
   └─ 当前任职人：工号 T2041 某老师
```

岗位先存在于组织中，再由真实自然人在一定时间内任职。人员离岗时岗位仍然存在，只是变为“空缺”或由代理人接任。

### 3.6 审核任务发送给组织队列，不绑定单个账号

学生或教职工注册申请应进入“软件工程 2023-1 班学生身份审核队列”或“计算机学院教职工身份审核队列”，而不是在创建申请时永久写死某个审核账号。

队列中的任何当前有效岗位成员都可以领取或处理。人员调动后未处理任务仍留在组织队列中，不会成为离职账号名下的孤儿任务。

### 3.7 正常流程不得依赖全局兜底

- 学院有负责人或身份审核员时，申请不得发送给平台管理员。
- 行政班有辅导员时，学生申请不得发送给教务。
- 只有岗位空缺、超时或组织数据异常时才升级处理。
- 系统必须把长期依赖兜底视为组织配置异常并产生待办。

## 4. 目标账号与身份模型

```text
app_user
└─ person_identity（一名自然人）
   ├─ student_identity（可选）
   ├─ staff_identity（可选）
   └─ teacher_identity（可选，属于教职工身份的教学扩展）

app_user
└─ user_role_binding（一个或多个岗位授权）
   └─ role_scope_binding（一个或多个授权范围）

organization_unit（学校、学院、部门）
└─ organization_position_slot（岗位编制）
   └─ position_assignment（自然人任职）

organization_review_queue（组织审核队列）
└─ review_task（注册、岗位和异常审核任务）
```

### 4.1 组织单元

新增统一的 `organization_unit`，避免只在不同业务表中散落 `college_id`：

| 字段 | 用途 |
| --- | --- |
| `id` | 组织单元 ID |
| `code` | 稳定组织编码 |
| `name` | 组织名称 |
| `unit_type` | `school/academic_office/college/department` |
| `parent_id` | 上级组织 |
| `status` | `active/merged/disabled` |
| `valid_from/valid_until` | 组织有效期 |

行政班继续由 `class_group` 表达，但必须关联所属学院组织单元。

### 4.2 自然人身份

新增统一的 `staff` 教职工目录，不再使用 `teacher` 代表全部工作人员。

建议关系：

```text
staff
  id
  staff_no
  name
  college_id
  department_code
  employment_status
  staff_type

teacher
  id
  staff_id
  teacher_no
  title
  hire_date
```

任课教师是教职工的一种扩展身份。行政人员可以存在于 `staff` 中而不必存在于 `teacher` 中。

### 4.3 岗位编制与任职

新增 `organization_position_slot`：

| 字段 | 用途 |
| --- | --- |
| `id` | 岗位编制 ID |
| `organization_unit_id` | 所属学校、学院或部门 |
| `position_code` | `college_primary_manager/college_deputy_manager/identity_reviewer/counselor/academic_officer/platform_admin` |
| `title` | 对外显示名称 |
| `min_occupants` | 最少任职人数 |
| `max_occupants` | 最大任职人数，可空 |
| `approval_policy` | 任命审批策略 |
| `status` | `active/vacant/disabled` |

新增 `position_assignment`，记录自然人在岗位上的任期：

| 字段 | 用途 |
| --- | --- |
| `position_slot_id` | 岗位编制 |
| `staff_id` | 任职自然人 |
| `assignment_type` | `primary/deputy/acting/temporary` |
| `valid_from/valid_until` | 任期 |
| `status` | `pending/active/suspended/ended` |
| `appointed_by` | 任命人 |
| `appointment_reason` | 任命依据 |

学院负责人不要求每个学院只有一个可操作人员。推荐每个学院具有：

- 1 名主要负责人 `primary`。
- 0-N 名分管负责人 `deputy`。
- 1-N 名教职工身份审核员 `identity_reviewer`。
- 必要时 1 名有明确期限的代理负责人 `acting`。

主要负责人、分管负责人和身份审核员的权限应不同。普通身份审核不需要全部由学院主要负责人亲自处理。

### 4.4 岗位授权

新增 `user_role_binding`：

| 字段 | 用途 |
| --- | --- |
| `id` | 岗位授权 ID |
| `user_id` | 被授权账号 |
| `role_code` | `student/teacher/counselor/college_manager/academic_office/admin` |
| `status` | `pending/active/suspended/revoked/expired` |
| `source` | `identity/teaching_assignment/position/manual/migration` |
| `granted_by_user_id` | 授权人 |
| `grant_reason` | 授权原因 |
| `valid_from` | 生效时间 |
| `valid_until` | 到期时间，可空 |
| `revoked_by_user_id` | 撤销人 |
| `revoked_at` | 撤销时间 |
| `revoke_reason` | 撤销原因 |
| `created_at/updated_at` | 审计时间 |

唯一约束不能只使用 `user_id + role_code`，因为同一角色可能有不同范围和任期。建议阻止同一用户出现时间重叠且范围完全相同的有效授权。

### 4.5 授权范围

新增 `role_scope_binding`：

| 字段 | 用途 |
| --- | --- |
| `role_binding_id` | 对应岗位授权 |
| `scope_type` | `self/teaching_class/class_group/college/academic_office/platform` |
| `scope_id` | 对应业务对象 ID；平台范围可空 |
| `created_at` | 创建时间 |

示例：

```text
李老师 · 任课教师
  scope_type = teaching_assignment
  实际课程范围按 teaching_class.teacher_id 动态计算

李老师 · 辅导员
  class_group = 软件工程 2023-1 班
  class_group = 软件工程 2023-2 班

王老师 · 学院负责人
  college = 计算机学院
```

### 4.6 组织审核队列

新增 `organization_review_queue` 和 `review_task`：

```text
计算机学院 · 教职工身份审核队列
数学与统计学院 · 教职工身份审核队列
软件工程 2023-1 班 · 学生身份审核队列
教务处 · 组织异常升级队列
平台运维 · 高风险账号队列
```

任务记录当前队列、领取人、处理人、状态、截止时间和升级路径。申请不永久绑定某个审核账号。

### 4.7 当前角色会话

Token 不直接信任前端传入的角色字符串。Token 中记录：

```json
{
  "sub": "user_id",
  "role_binding_id": 123,
  "session_version": 4,
  "exp": 1234567890
}
```

每次请求后端必须确认：

1. 账号处于 `active`。
2. `role_binding_id` 属于当前账号。
3. 岗位授权处于 `active` 且未过期。
4. 账号的 `session_version` 未变化。

岗位撤销、密码修改或账号停用时递增 `session_version`，让旧 Token 立即失效。

## 5. 岗位产生方式

### 5.1 学生

- 来源：学生身份审核通过。
- 授权人：所属辅导员或教务。
- 范围：本人 `student_id`。
- 默认长期有效，学籍离校或停用后失效。

### 5.2 任课教师

- 来源：教职工身份审核通过，并存在教师身份或教学任务。
- 授权人：学院负责人或教学任务同步程序。
- 范围：根据 `teaching_class.teacher_id` 动态计算。
- 没有当前课程时仍可保留教师身份，但首页显示无当前授课任务，而不是越权查看其他课程。

### 5.3 辅导员

- 来源：学院岗位任命。
- 可授权人：本学院负责人、教务处老师、管理员。
- 必填范围：至少一个行政班。
- 可选有效期：岗位轮换结束日期。
- 行政班转交时支持批量移交给下一位辅导员。
- 每个在用行政班必须至少有一名主要辅导员；允许配置协同辅导员。
- 学院工作台显示未配置辅导员的行政班，并要求限期补齐。

### 5.4 学院负责人

- 来源：学院岗位任命。
- 可授权人：教务处老师、管理员。
- 必填范围：至少一个学院。
- 不允许学院负责人给自己增加其他学院范围。
- 一个学院可以有一名主要负责人、多名分管负责人和身份审核员，不能用一个全校共享的 `college` 账号替代。
- 主要负责人空缺时允许设置有明确到期时间的代理负责人。
- 学院身份审核可以委派给身份审核员，降低主要负责人逐条处理压力。

### 5.5 教务处老师

- 来源：教务岗位任命。
- 可授权人：管理员。
- 范围：教务管理授权范围。
- 不默认获得平台数据治理或账号管理权限。
- 教务处必须至少有两名有效工作人员，避免所有升级任务集中到单一 `jwc` 账号。

### 5.6 平台管理员

- 来源：平台运维任命。
- 可授权人：已有管理员。
- 范围：平台运维。
- 不因为管理员身份自动获得学生提交正文、辅导员私密记录等教学隐私。
- 正式环境至少保留两名绑定真实工号的管理员，泛化账号 `admin` 只用于本地演示。

### 5.7 组织岗位覆盖规则

系统持续检查以下组织配置：

| 对象 | 最低覆盖要求 | 缺失处理 |
| --- | --- | --- |
| 每个学院 | 1 名主要负责人或有效代理负责人 | 生成教务组织异常，不把日常任务直接丢给管理员 |
| 每个学院 | 1 名以上身份审核员 | 申请暂存学院队列并提醒主要负责人 |
| 每个在用行政班 | 1 名主要辅导员 | 申请进入学院学生工作队列并生成配置异常 |
| 教务处 | 2 名有效教务工作人员 | 提醒管理员补充任命 |
| 平台运维 | 2 名有效管理员 | 禁止撤销至低于安全人数 |

覆盖规则的阈值允许配置，但不能完全关闭最后管理员保护。

## 6. 授权矩阵

| 操作者 | 任课教师 | 辅导员 | 学院负责人 | 教务处老师 | 管理员 |
| --- | --- | --- | --- | --- | --- |
| 学院负责人 | 本学院确认 | 本学院授权 | 无权 | 无权 | 无权 |
| 教务处老师 | 可确认 | 可授权 | 可授权 | 无权 | 无权 |
| 管理员 | 可处理异常 | 可处理异常 | 可授权 | 可授权 | 可授权 |

学院内部进一步区分：

| 学院岗位 | 教职工身份审核 | 辅导员任命 | 学院范围调整 | 学院高风险审批 |
| --- | --- | --- | --- | --- |
| 主要负责人 | 可处理 | 可处理 | 仅提交上级审批 | 可处理 |
| 分管负责人 | 可处理 | 按分工处理 | 无权 | 按授权处理 |
| 身份审核员 | 可批量处理 | 无权 | 无权 | 无权 |
| 代理负责人 | 在有效期内按任命范围处理 | 在有效期内处理 | 无权 | 按任命范围处理 |

补充限制：

- 普通教师和学生没有岗位授权入口。
- 学院负责人只能操作本学院教职工和行政班。
- 教务处老师不能授予管理员。
- 管理员授权和撤销必须二次验证密码。
- 操作者不能审批或授权自己提交的高权限岗位申请。

## 7. 产品流程

### 7.1 教职工首次注册

```text
输入工号、姓名和密码
→ 匹配 staff 目录
→ 申请进入所属学院教职工身份审核队列
→ 学院主要负责人、分管负责人或身份审核员批量确认
→ 账号获得“已验证教职工”基础身份
→ 如果存在授课任务，自动产生任课教师角色
→ 如果没有岗位授权，只能进入个人中心和岗位状态页
```

“教职工”是基础身份，不等同于任课教师角色。

如果学院岗位空缺，申请保留在学院队列并产生组织异常；只有超过处理时限后才升级到教务队列，不能在提交时直接绑定管理员账号。

### 7.2 授予辅导员岗位

```text
学院负责人进入“组织与岗位”
→ 选择已验证教职工
→ 选择“辅导员”
→ 选择一个或多个本学院行政班
→ 填写任命依据和有效期
→ 确认授权
→ 用户收到通知
→ 下次登录可切换到辅导员工作台
```

### 7.3 授予学院负责人或教务岗位

流程与辅导员类似，但范围和授权人不同：

- 学院负责人必须选择学院。
- 教务处老师不由普通学院负责人授权。
- 高权限授权不能批量跨组织执行。
- 任命学院负责人时必须选择具体学院、任职类型和任期，不能创建一个无学院范围的“全校学院负责人”。
- 同一学院新增主要负责人时，系统必须处理原主要负责人的结束、转任或代理状态，不能同时出现多个未解释的主要负责人。

### 7.4 授予管理员

```text
管理员选择已验证教职工
→ 选择平台管理员岗位
→ 填写授权原因
→ 重新输入当前管理员密码
→ 系统检查授权后仍至少存在一名有效管理员
→ 创建授权并使被授权人的旧会话失效
→ 写入高风险审计日志
→ 新管理员首次使用管理员角色时强制修改密码
```

### 7.5 角色切换

当账号拥有多个有效角色时，登录后显示身份选择页：

```text
请选择本次工作身份

[任课教师]
数据库系统、Web 开发技术

[辅导员]
软件工程 2023-1 班、2023-2 班
```

切换角色必须请求后端生成新的角色会话，不能只在前端切换菜单。

### 7.6 撤销、到期和交接

- 到期岗位由定时任务标记为 `expired`。
- 撤销必须填写原因。
- 辅导员撤销前提示仍由其负责的行政班，并支持转交。
- 学院负责人撤销前检查是否存在待审批事项。
- 管理员撤销前检查是否为最后一个有效管理员。
- 撤销后递增账号 `session_version`，当前岗位 Token 立即失效。

## 8. 页面设计

### 8.1 我的身份

所有已登录用户可见：

- 已验证自然人身份。
- 当前拥有的岗位角色。
- 每个角色的授权范围和有效期。
- 当前使用中的角色。
- 切换角色入口。
- 已失效或待生效岗位记录。

### 8.2 组织人员目录

不同角色看到不同范围：

- 辅导员：所带行政班学生及账号激活状态。
- 学院负责人：本学院教职工、教师及岗位状态。
- 教务处：全校学院和教职工岗位汇总。
- 管理员：账号运行状态和必要身份字段，不默认查看教学隐私。

页面支持筛选：

```text
未注册 / 待审核 / 已激活 / 已停用
无岗位 / 任课教师 / 辅导员 / 学院负责人 / 教务 / 管理员
```

组织目录还应提供岗位覆盖视图，直接显示每个学院是否具备主要负责人、身份审核员和足够的辅导员。例如：

| 学院 | 主要负责人 | 身份审核员 | 辅导员覆盖 | 待审核 | 异常 |
| --- | --- | --- | ---: | ---: | --- |
| 计算机学院 | 李老师 | 2 人 | 18/18 班 | 12 | 无 |
| 数学与统计学院 | 空缺 | 0 人 | 3/16 班 | 46 | 负责人空缺 |

系统应优先暴露岗位缺口，而不是让教务在待审核列表中被动发现大量兜底申请。

### 8.3 岗位授权工作台

- 待授权或待确认人员。
- 当前岗位成员。
- 即将到期岗位。
- 行政班或学院范围缺失异常。
- 授予、调整范围、续期、撤销和交接操作。
- 按学院、部门和行政班批量建立岗位编制。
- 将待审核任务从离任人员转回组织队列或移交给继任者。

### 8.4 我的审核队列

- 展示当前岗位可以处理的组织任务，而不是只展示分配给某个固定账号的任务。
- 支持全选正常匹配申请、批量通过和批量拒绝。
- 姓名不一致、重复绑定、跨组织等异常项不能混入一键通过。
- 支持领取任务，但领取只用于协作，不改变任务所属组织。
- 显示处理时限、即将超时和升级状态。

### 8.5 管理员安全确认弹窗

管理员授权必须显示：

- 被授权人姓名和工号。
- 将获得的具体运维权限。
- 不包含的教学隐私权限。
- 当前管理员密码输入框。
- 授权原因。

批量审核以队列和当前岗位范围为边界，不能跨学院拼接申请 ID。

## 10. 数据迁移方案

### 10.1 迁移原则

- 迁移使用可重复执行脚本。
- 先建立新绑定，再切换认证读取逻辑。
- 新旧结构并行验证一轮后，最后停止读取 `app_user.role`。
- 不直接删除已有演示账号和历史审计数据。

### 10.2 迁移步骤

迁移必须先补齐组织结构，而不是直接迁移现有单一 `college` 账号：

1. 新建 `organization_unit`，迁移学校、6 个学院和教务处组织结构。
2. 为每个学院建立主要负责人、分管负责人、身份审核员和辅导员岗位编制。
3. 新建组织审核队列，并把注册申请从“指定审核账号”迁移为“所属组织队列”。

1. 新建 `staff`、`person_identity`、`user_role_binding`、`role_scope_binding`。
2. 将现有 `teacher` 转换为 `staff + teacher` 关系。
3. 为现有辅导员创建 `staff` 身份，并迁移行政班关系。
4. 根据 `app_user.role` 为每个现有账号生成一个 `user_role_binding`。
5. 将 `student_id/teacher_id/counselor_id/college_id` 转换为身份绑定和范围绑定。
6. 为 `admin`、`jwc`、`college` 等账号生成 `source=migration` 的岗位授权。
7. 登录接口改为读取有效岗位绑定。
8. Token 增加 `role_binding_id` 和 `session_version`。
9. 前端增加角色选择和切换。
10. 验证稳定后停止使用 `app_user.role` 作为权限事实源。

现有迁移步骤中，`admin`、`jwc`、`college` 只迁移为本地演示兼容账号，不作为正式岗位自然人。正式岗位必须重新绑定真实工号。

### 10.3 演示数据调整

阶段完成后，演示数据不能继续只有一个 `college` 账号。至少准备：

- 6 个学院各 1 名具名主要负责人。
- 6 个学院各 1 名具名身份审核员；负责人可以兼任，但岗位记录必须分开。
- 每个演示行政班至少 1 名辅导员。
- 2 名教务处工作人员，用于队列协作和交接测试。
- 2 名平台管理员，用于最后管理员保护测试。
- 至少 1 名同时担任教师和辅导员的多角色用户。

这些账号均使用真实风格工号作为登录标识。泛化账号仅保留在显式 `DEMO_MODE` 中。

## 11. 安全与审计要求

每次岗位操作记录：

- 操作者账号、自然人和当前角色。
- 被操作账号和自然人。
- 岗位类型。
- 授权范围变更前后值。
- 原因、时间、客户端信息。
- 成功或失败结果。

必须覆盖以下安全规则：

1. 用户不能给自己授予管理角色。
2. 学院负责人不能操作其他学院。
3. 辅导员不能授予岗位。
4. 教务不能授予管理员。
5. 管理员授权必须二次验证。
6. 系统始终至少保留一名有效管理员。
7. 岗位撤销和账号停用立即使对应会话失效。
8. 角色切换后不能继续使用上一个角色的接口范围。
9. 管理员不默认获得教学隐私字段权限。
10. 批量操作逐项进行范围校验，不允许混入越权对象。
11. 禁止多个自然人共享一个正式账号。
12. 岗位空缺时申请保留在组织队列，不自动扩大普通管理员的数据访问范围。
13. 代理岗位到期后自动失效，不能永久残留。
14. 学院主要负责人和审核员只能处理绑定学院的队列。
15. 密码重置、解锁和账号恢复必须记录操作者与原因。

### 11.1 账号安全与恢复

- 学号或工号是登录标识，密码只保存强哈希。
- 连续失败达到阈值后短期锁定，并记录风险事件。
- 密码重置优先使用校园统一认证、预留邮箱或手机号。
- 未接入外部认证前，由组织身份审核员发起重置，用户自行设置新密码；审核员不能看到新密码。
- 高权限账号重置密码后撤销全部旧会话，并通知其他管理员。
- 正式账号不得使用 `admin`、`college` 等角色名称作为登录标识。

### 11.2 人员和组织生命周期

- 学生毕业后保留必要历史访问，但撤销新增教学操作权限。
- 教职工离职后立即结束全部岗位任职和角色绑定。
- 教职工跨学院调动时，旧学院岗位不自动迁移到新学院。
- 学院合并或更名通过组织版本迁移处理，不能直接覆盖历史名称。
- 行政班变更后重新计算辅导员范围，并列出需要人工确认的冲突。

## 12. 自动化测试

### 12.1 身份与岗位测试

- 非教师教职工可以注册并完成基础身份验证。
- 有教学任务的教职工获得任课教师角色。
- 没有教学任务的教职工不能查看任意课程。
- 同一账号可以同时拥有教师和辅导员角色。

### 12.2 授权范围测试

- 学院负责人只能给本学院人员授权。
- 辅导员岗位只能绑定授权学院的行政班。
- 学院负责人不能跨学院扩展自己的范围。
- 教务岗位和管理员岗位不能由低权限角色授予。
- 6 个学院的负责人只能看到各自学院。
- 一个学院的多个审核员可以处理同一组织队列，但不能处理其他学院队列。
- 代理负责人到期后不能继续审核。

### 12.3 角色切换测试

- 切换教师后只能访问本人课程。
- 切换辅导员后只能访问所带行政班。
- 旧角色 Token 在岗位撤销后失效。
- 前端隐藏菜单不能代替后端权限验证。

### 12.4 管理员安全测试

- 错误二次验证密码不能授权管理员。
- 不能撤销或停用最后一个管理员。
- 管理员授权和撤销均产生高风险审计记录。
- 管理员不能通过运维角色读取教学隐私正文。

### 12.5 迁移回归测试

- 现有 15 个演示账号仍可登录。
- 演示账号迁移后的角色和范围与迁移前一致。
- 当前注册、身份审批、首页、作业和学习支持流程不回退。
- 6 个学院均有独立具名负责人或明确显示岗位空缺。
- 泛化演示账号不会出现在正式组织岗位成员列表中。

### 12.6 账号生命周期测试

- 连续登录失败触发锁定，解锁有审计记录。
- 学生毕业、教职工离职和跨学院调动能够正确收回权限。
- 密码重置后旧 Token 失效。
- 组织队列任务不会因审核人员离职而丢失。

- 真实演示库迁移结果为 26 个有效账号、0 个缺失绑定、0 个缺失范围、0 个泛化正式岗位占用。
- 完整自动化回归为 103 项通过。

验收：无需手工维护数据库即可完成普通注册、身份审核、岗位授权、多角色切换、岗位撤销和管理员安全管理。

## 14. 完成标准

1. 所有教职工均来自统一教职工目录，不再要求行政人员伪装成教师。
2. 辅导员、学院负责人、教务和管理员均可通过正式产品流程新增。
3. 一个账号可以拥有多个岗位角色，并安全切换当前角色。
4. 每个角色的数据范围均来自岗位关系或业务关系，而不是前端参数。
5. 高权限岗位授权、范围调整、续期和撤销都有完整审计。
6. 系统不能停用最后一个管理员。
7. 岗位撤销、账号停用和密码修改能够使相关旧会话失效。
8. 现有注册、审批、工作台和教学流程保持兼容。
9. 6 个学院都有独立岗位编制、审核队列和负责人覆盖状态。
10. 正式环境不存在多人共享的 `college`、`jwc` 或 `admin` 角色账号。
11. 注册申请优先进入所属组织队列，只有超时或岗位空缺时才按规则升级。
12. 密码重置、账号锁定、毕业、离职和跨学院调动均有可执行的生命周期流程。

完成本阶段后，系统才具备可持续扩展的真实账号、组织和岗位权限基础，可继续进入通知中心与课程空间阶段。

## 15. 后续账号退出生命周期

B.6 已完成岗位任职结束和角色绑定撤销，但学生离校、职工离职、跨组织调动、账号安全停用和用户主动销户仍需要统一的账号与身份生命周期服务。后续设计见 [B.7 账号、身份与岗位退出生命周期方案](account_identity_lifecycle_plan.md)。该方案属于待开发内容，不应视为当前已经实现的功能。
