# NL2SQL 项目演示与验收交接方案

更新日期：2026-07-30
适用版本：`9527-final`

## 1. 文档目的

本文件用于四名项目成员进行现场演示、功能验收和答辩准备。验收采用“一人一次、完整讲完”的方式：每名成员只出场一次，在自己的时间段内完成模块介绍、操作演示、技术说明、权限验证和验收结论。

成员不得将本人未实际参与的历史开发工作描述为本人完成。建议根据实际情况使用以下表述：

> 本人负责本次版本中该模块的功能复核、演示准备、验收执行、技术梳理和问题闭环。

实际编写或修改过的代码、测试、文档，可以在此基础上如实补充。

## 2. 固定出场顺序

现场必须严格按照以下顺序执行。前一名成员结束后不再返场补充。

| 顺序 | 成员 | 负责范围 | 验收定位 |
|---|---|---|---|
| 1 | 成员 A（项目主负责人） | 项目架构、账号身份、组织岗位、生命周期、教学运行管理 | 平台架构与权限体系 |
| 2 | 成员 C | 教师—学生教学业务、课程空间、作业、考勤、答疑、通知、课程分析、学生支持 | 教学业务闭环 |

## 3. 演示前统一准备

### 3.1 环境准备

- 确认演示代码为 `9527-final`。
- 记录当前提交号和工作区状态。
- 启动 FastAPI 服务并确认 `/api/health` 返回正常。
- 提前登录并验证管理员、教务、学院、教师、学生和辅导员六类业务身份。
- 浏览器使用全新或已清理缓存的配置，避免旧 JavaScript 资源影响演示。
- 准备一份可恢复的 `data/teaching.db` 演示副本。
- 准备一个可丢弃的 SQLite 文件和一个只读 PostgreSQL 测试库；如未准备，不得现场临时连接未知数据库。

### 3.2 演示数据命名

所有现场新增数据必须使用唯一前缀：

```text
DEMO-<日期>-<成员>-<业务名称>
```

例如：

```text
DEMO-0731-C-课程公告
DEMO-0731-C-作业
DEMO-0731-A-岗位任职
DEMO-0731-B-SQLite
```

### 3.3 统一验收原则

- 页面显示正确只是第一层证据，关键权限必须补充一次后端拒绝证据。
- 写操作成功后应展示数据状态变化；拒绝用例应确认数据没有变化。
- 大模型结果不能仅凭自然语言判断，应同时核对 SQL、结果集、身份范围和数据来源。
- 不将条件可用、后端限定或未实现能力描述为完整产品功能。

# 第一部分：成员 A——平台架构、身份权限与教学管理

## 4. 本部分验收目标

成员 A 需要证明系统具备完整的平台基础：用户可以注册和登录，身份与组织岗位决定权限，人员状态变化会影响账号和业务授权，管理角色可以在各自范围内完成教学运行和成绩审核。

该部分同时承担整场演示的项目开场，不再在后续环节返场补充架构内容。

## 5. 成员 A 完整演示链路

### 5.1 项目定位与技术架构

首先说明项目定位：

- 项目面向高校教学管理场景。
- 系统不仅提供自然语言转 SQL，还包括身份权限、课程教学、作业考勤、学生支持、知识治理和外部数据接入。
- 后端采用 FastAPI，数据访问使用 SQLite/PostgreSQL 与 SQLAlchemy，模型侧使用 DashScope/Qwen，前端采用原生 HTML/CSS/JavaScript 单页应用。

建议使用以下调用关系进行说明：

```text
浏览器单页应用
    ↓
FastAPI 路由层
    ↓
身份认证与 AuthContext
    ↓
业务服务层
    ↓
SQLite / PostgreSQL / 模型与检索服务
```

### 5.2 登录、注册和身份选择

操作步骤：

1. 展示登录页面。
2. 使用一个已有账号登录，展示当前用户信息、当前工作身份和导航菜单。
3. 展示学生或普通职工自助注册入口。
4. 说明注册申请不会直接获得高权限角色，需要进入审核队列。
5. 展示注册进度查询。
6. 使用具有多个合法身份的账号展示工作身份选择与切换。
7. 切换身份后说明旧身份的页面能力和会话不能继续复用。
8. 进入个人中心，展示身份概览、账号状态、数据范围和修改密码入口。

预期结果：

- 登录成功后由服务端返回当前角色允许的导航。
- 待审核用户不能访问业务数据。
- 角色切换后服务端按新角色重新生成权限范围。
- 当前工作身份不等于用户永久拥有全部角色权限。

### 5.3 组织、岗位和审核队列

操作步骤：

1. 以管理员或具有组织管理能力的角色进入组织管理。
2. 展示学校、教务处、学院、行政班等组织单元。
3. 展示职工目录、岗位槽位、任职人和岗位覆盖状态。
4. 选择一个演示岗位，展示新建任职。
5. 展示任职续期、结束和转任入口。
6. 在结束任职前展示影响预览。
7. 展示审核队列及队列任务。
8. 展示学院审核员只能处理被授权学院的申请。

预期结果：

- 权限由“人员身份 + 岗位任职 + 角色绑定 + 数据范围 + 当前工作身份”共同决定。
- 学院角色仅能访问本学院人员和申请。
- 岗位结束或转任会同步考虑角色绑定、会话和待办交接。

### 5.4 账号与人员生命周期

操作步骤：

1. 展示某个已核验人员的生命周期详情。
2. 展示账号事件影响预览。
3. 演示管理员安全冻结测试账号：
   - 填写冻结依据；
   - 进行二次身份验证；
   - 确认旧会话立即失效。
4. 演示恢复安全冻结，说明恢复不会自动复活已经撤销的岗位授权。
5. 展示学生休学、复学、毕业和退学入口。
6. 展示批量毕业的整批预校验逻辑。
7. 展示职工离职、退休或跨学院调动的双确认流程。

预期结果：

- 安全冻结会立即撤销现有会话。
- 休学、毕业、退学等状态变化不会删除历史作业、成绩和审计事实。
- 高风险职工事项需要两名具名管理员确认，不能由同一人自行发起并确认。

### 5.5 角色首页和教学运行

操作步骤：

1. 分别简要展示管理员、教务和学院负责人的角色首页。
2. 进入教学运行页面。
3. 展示教学任务台账中的课程、学院、教师、学年学期、教室、容量、选课人数和成绩状态。
4. 演示关键词、学年、学期、学院和成绩状态组合筛选。
5. 演示筛选重置和结果数量变化。
6. 展示未排教室、超容量和低选课异常。
7. 以教务或所属学院身份将异常标记为处理中或填写解决说明。
8. 演示跨学院处理被拒绝。

### 5.6 成绩管理闭环

操作步骤：

1. 展示教师完成课程成绩提交。
2. 切换到学院角色，审核成绩提交。
3. 切换到教务角色，发布成绩。
4. 展示退回或拒绝时的原因记录。
5. 说明每个角色只能在自己的范围和状态节点执行动作。

预期状态流：

```text
教师提交
  ↓
学院审核
  ↓
教务发布
```

成员 A 完成成绩管理说明后结束本部分，不再在后续成员演示期间返场。

## 6. 成员 A 必须掌握的内容

### 6.1 业务概念

- 用户、人员身份、账号、角色和岗位不是同一个概念。
- 同一个人可以拥有多个合法角色，但每次请求只使用当前工作身份。
- 学院负责人、教师和辅导员的权限范围分别落在学院、授课班和行政班。
- 生命周期操作需要保留业务历史，不应直接删除成绩、作业或审计数据。

### 6.2 技术概念

- `AuthContext` 是后端业务权限判断的统一上下文。
- 导航菜单来自服务端能力计算，前端不能自行扩大权限。
- API 即使被直接调用，仍会在后端进行角色和数据范围校验。
- 数据库迁移在启动时按版本执行，并要求幂等和失败回滚。

### 6.3 重点源码

- `app/main.py`：应用入口与路由挂载。
- `app/api/routes.py`：认证、用户、工作台和主要公共 API。
- `app/core/business_domains.py`：角色、业务域、表字段限制和数据范围。
- `app/core/organization_access.py`：组织、岗位、任职和审核队列。
- `app/core/identity_registration.py`：注册申请与审核。
- `app/core/lifecycle.py`：安全冻结、学籍和职工生命周期。
- `app/core/stage_e.py`：教学运行异常和成绩管理。

## 7. 成员 A 常见答辩问题

| 问题 | 回答要点 |
|---|---|
| 为什么不能只用一个角色字段？ | 实际高校组织中一个人可能同时担任教师、辅导员或管理岗位，权限还要受学院、课程、行政班和任职有效期限制，因此需要角色绑定和数据范围模型。 |
| 前端隐藏菜单是否等于安全？ | 不等于。菜单隐藏只改善体验，后端每个业务接口仍会校验当前身份和数据范围。 |
| 冻结账号与结束岗位有什么区别？ | 冻结针对账号安全，立即撤销会话；结束岗位针对组织任职，会影响对应角色授权和业务交接。 |
| 学生毕业后历史成绩是否删除？ | 不删除。账号和业务权限会调整，但历史成绩、作业、审批和审计事实继续保留。 |

## 8. 成员 A 验收证据

- 不同身份登录后的角色标签和导航截图；
- 一次跨学院访问被拒绝的接口或页面证据；
- 岗位影响预览和任职状态变化证据；
- 安全冻结后旧会话失效证据；
- 教学运行筛选结果；
- 成绩提交、学院审核和教务发布的状态记录。

# 第二部分：成员 C——教师与学生教学业务闭环

## 9. 本部分验收目标

成员 C 需要证明平台能够完成从教师准备课程内容，到学生学习、提交、获得反馈，再到考勤、答疑、通知和学生支持的完整教学闭环。

## 10. 成员 C 完整演示链路

### 10.1 教师课程空间

操作步骤：

1. 以教师身份登录。
2. 展示教师首页和本人课程列表。
3. 进入一门本人任课课程的课程空间。
4. 创建一条带唯一标识的课程公告并发布。
5. 上传一个允许格式、20MB 以内的课程附件，或登记 HTTP(S) 外部链接。
6. 展示公告和资料已经出现在课程空间。
7. 展示教师可查看公告送达/已读汇总。

### 10.2 教师创建并发布作业

操作步骤：

1. 在当前课程创建作业草稿。
2. 设置标题、说明和截止时间。
3. 修改一次草稿，说明草稿阶段允许编辑。
4. 发布作业。
5. 说明发布后学生端才进入可见状态。

### 10.3 学生查看并提交作业

操作步骤：

1. 退出教师身份，登录已选该课程的学生账号。
2. 从通知中心或课程空间查看教师公告。
3. 下载课程资料。
4. 查看已发布作业。
5. 提交文本内容和/或附件。
6. 在规则允许时进行重新提交。
7. 展示版本记录保留原提交和原附件信息。
8. 尝试访问不属于本人的作业或其他学生提交，展示安全拒绝。

### 10.4 教师评分与成绩发布

操作步骤：

1. 切回教师身份。
2. 查看作业提交名单。
3. 对学生提交进行评分并填写反馈。
4. 如需要，演示退回学生重交。
5. 发布该作业成绩。
6. 切换到学生身份，展示本人分数、反馈和对应通知。

状态关系：

```text
教师草稿 → 教师发布 → 学生提交/重交
→ 教师退回或评分 → 教师发布成绩 → 学生查看
```

### 10.5 课程场次与考勤

操作步骤：

1. 教师为本人课程创建真实课程场次。
2. 填写日期、时间、教室和主题。
3. 获取实际选课名单。
4. 批量登记出勤、迟到、请假或缺勤。
5. 再次保存一次考勤修正。
6. 切换到学生身份，展示本人课程场次和本人考勤。
7. 确认学生不能查看同班名单或其他学生考勤。

### 10.6 课程答疑

操作步骤：

1. 学生创建一条公开问题。
2. 学生再创建一条私密问题。
3. 教师进入课程答疑页面进行回复。
4. 展示追问、关闭和置顶能力。
5. 使用另一名学生验证私密问题不可见。

### 10.7 通知和安全跳转

操作步骤：

1. 展示当前学生的通知未读数。
2. 打开公告、作业、答疑或成绩通知。
3. 点击“查看详情”。
4. 确认系统先将本人通知标记为已读，再跳转至后端提供的安全业务页面。
5. 验证用户不能通过修改前端目标跳转到无权资源。

### 10.8 课程分析

操作步骤：

1. 教师查看本人授课班课程分析。
2. 学生查看本人课程上下文。
3. 展示预计算摘要、指标说明和模板化教学问题。
4. 说明复杂问题可以在权限范围内回退至 NL2SQL，但该链路由成员 D 统一讲解。

### 10.9 学生支持与辅导员

操作步骤：

1. 学生创建咨询或预约请求。
2. 展示请求根据行政班关系路由到对应辅导员。
3. 切换到辅导员身份，查看本人负责班级的支持个案和预约请求。
4. 展示个案触发原因、考勤/作业证据、建议行动、跟进时间和学生反馈。
5. 更新个案状态或填写联系人记录。
6. 尝试查看非本人负责行政班的学生，展示拒绝。

成员 C 完成学生支持后结束本部分。

## 11. 成员 C 必须掌握的内容

### 11.1 业务状态

- 公告草稿、发布和软删除的区别。
- 作业草稿、发布、学生提交、退回、重交、评分和成绩发布的顺序。
- 学生“未完成作业”不等于“未截止作业”。
- `late` 表示已有迟交记录，不能直接视为未提交。
- 考勤修正是有审计记录的覆盖，不是无痕删除旧事实。
- 公开答疑和私密答疑的可见范围不同。

### 11.2 权限范围

- 教师只能管理本人实际任课课程。
- 学生只能访问本人选课课程和本人提交。
- 学生不能读取同班名单或他人考勤。
- 辅导员只能查看被分配行政班学生的必要支持事实。
- 课程公告和资料下载也必须校验课程成员关系。

### 11.3 技术实现

- 前端使用 `app/static/app.js` 调用 FastAPI API。
- `app/api/teaching.py` 提供教学业务接口。
- `app/core/assignment_workflow.py` 实现作业状态机。
- `app/core/course_space.py` 实现公告、资料、送达和成员鉴权。
- `app/core/stage_d.py` 实现场次、考勤和答疑。
- `app/core/course_analytics.py` 实现课程分析上下文。
- `app/core/support_workflow.py` 实现支持个案、咨询和预约。

## 12. 成员 C 常见答辩问题

| 问题 | 回答要点 |
|---|---|
| 学生能否查看同学的作业和成绩？ | 不能。后端以当前学生身份校验提交归属，列表和详情都限制为本人。 |
| 教师能否操作其他教师的课程？ | 不能。每次操作都会校验教师与教学班的真实任课关系。 |
| 公告删除后为何还保留记录？ | 使用软删除既能让学生端立即下线，又能保留送达和审计证据。 |

### 20.4 本版本优化修复说明

成员 B 需要按“问题—原因—修改—验证”说明以下重点：

#### 多表学生范围

- 原问题：一个查询块中只要出现一个正确学生条件，其他学生相关表可能未被限制。
- 修改：逐表识别学生范围节点，并通过明确的等值连接传播范围。
- 验证：未限制提交表别名的 SQL 被拒绝，合法连接可以通过。

#### 合法 OR

- 原问题：所有带 `OR` 的学生范围 SQL 都被拒绝，正常业务状态查询也无法执行。
- 修改：允许括号内的业务 `OR`，但身份范围必须作为顶层独立 `AND`。
- 验证：合法业务 OR 通过，顶层 OR 绕过仍被拒绝。

#### 未完成作业口径

- 原问题：模型可能用提交表内连接，漏掉完全没有提交记录的作业；还可能把 `late` 误认为未提交。
- 修改：提示词、Schema 画像和执行前语义校验共同限制 `LEFT JOIN`/`NOT EXISTS`、状态范围和日期条件。
- 验证：无提交、退回、迟交和日期边界用例均有回归测试。

#### 会话追问

- 原问题：统一助手只校验会话页面，没有读取服务端历史。
- 修改：按当前用户和工作身份读取最近有效轮次，并锁定页面与数据源。
- 验证：追问保留主题，跨用户、跨角色、跨数据源被拒绝。

#### 敏感身份和无法回答

- 原问题：模型返回单列 `error` 时可能被前端展示为成功结果。
- 修改：身份证号等敏感词在模型前拒绝；无法回答占位转换为“不支持”。
- 验证：不调用模型、不执行 SQL、不展示导出动作。

| PostgreSQL 为什么不能直接填写密码？ | 避免密码进入浏览器请求、配置文件、日志和返回结果，系统只保存环境变量名。 |
| 只读账号是否足够？ | 不足。数据库账号只读、连接只读事务、应用写接口拒绝和 SQL 校验共同构成多层保护。 |
| 为什么合法 OR 可以通过？ | 业务状态可能需要 OR，但身份范围必须作为顶层独立 AND，不能让 OR 改变权限条件的结合范围。 |
| 测试通过是否代表生产可用？ | 不代表。当前结论只覆盖指定版本、环境、数据和用例，生产部署还需性能、容量、灾备和真实组织集成验证。 |

## 24. 当前实现边界

- BIRD 已从当前项目运行能力中移除。仓库不包含 BIRD 数据库、下载器、专用连接或一键完整评测脚本；现有文档中的 BIRD 内容属于历史测试记录或外部准备说明。
- server 四路检索属于条件可用能力，依赖 Docker 和外部服务。
- PostgreSQL 当前支持只读注册、Schema 扫描、表预览和问数；不支持编辑、保存、删除、搜索、排序、导出或 PostgreSQL schema 选择。
- V3 认证指标语义层包含后端/API 能力，但并非全部指标都有独立前端页面。
- 系统没有短信、邮件、企业微信或统一身份认证平台的真实集成。
- 系统没有完整的忘记密码短信/邮件自助重置流程。
- 模型结果存在非确定性，验收结论必须依赖 SQL、结果集、权限范围和错误码。
