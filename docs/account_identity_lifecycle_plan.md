# B.7 账号、身份与岗位退出生命周期方案

> 方案日期：2026-07-17
> 方案性质：待开发设计，不代表当前功能已经实现
> 前置基础：B.6 组织岗位授权、多角色与迁移闭环

## 1. 结论

当前角色管理确实缺少完整的退出能力，但产品上不应只增加一个“注销”按钮。

“岗位调整”“学生离校”“教职工离职”“账号安全停用”“用户主动销户”是五种不同事件。它们对登录、人员身份、角色权限、历史数据和恢复方式的影响不同，必须分开建模：

| 用户口中的操作 | 系统正式含义 | 是否删除人员 | 是否保留账号 | 是否保留历史业务数据 |
|---|---|---:|---:|---:|
| 不再担任辅导员/负责人 | 结束岗位任职 | 是（仅移出岗位） | 是 | 是 |
| 调到其他学院/岗位 | 原子调岗或转任 | 否 | 是 | 是 |
| 学生休学 | 暂停在读业务资格 | 否 | 是 | 是 |
| 学生毕业/退学 | 结束当前学籍关系 | 否 | 是或转只读 | 是 |
| 教职工离职/退休 | 结束任职关系 | 否 | 归档或转只读 | 是 |
| 账号疑似被盗 | 安全停用 | 否 | 是 | 是 |
| 用户不再使用系统 | 主动销户 | 否 | 关闭登录凭据 | 是 |
| 删除错误的待审核申请 | 清理未形成业务关系的数据 | 视情况 | 否 | 只保留必要审计 |

系统默认不物理删除已经产生业务记录的账号或人员。作业、成绩、考勤、任职、审批、支持记录和审计必须继续指向稳定的人员 ID。

## 2. 当前能力与缺口

### 2.1 已有能力

- 可以结束、续期和转移岗位任职。
- 岗位结束后撤销对应角色绑定并使旧会话失效。
- 临时/代理任职可以到期自动失效。
- 密码修改会撤销旧会话。
- 连续登录失败会临时锁定。
- 注册审核和岗位操作已有审计基础。

### 2.2 仍然缺少

- 没有账号停用、恢复、归档和主动销户的正式接口与页面。
- `student.status` 和 `staff.employment_status` 只用于局部查询，没有驱动统一撤权。
- 没有休学、复学、毕业、退学、离职、退休和返聘的可执行状态流程。
- 调岗只覆盖具体岗位交接，没有覆盖人员所属学院变化及全部旧范围检查。
- 没有离校/离职前的影响预览和未完成事项移交。
- 没有把注册审核任务、支持个案、课程责任等重新分配给组织队列或接任人。
- 没有销户冷静期、撤回、恢复和重新激活机制。
- 没有明确区分业务资格失效与账号安全封禁。
- 当前已验证学生只有学生业务角色，业务资格暂停后缺少只访问个人安全/生命周期页面的基础身份。

## 3. 产品原则

### 3.1 账号、自然人、校内关系和岗位分别处理

```text
登录账号 app_user
  └─ 自然人 person_identity
       ├─ 学籍/任职关系 person_affiliation
       └─ 组织岗位 position_assignment
            └─ 业务角色 user_role_binding
```

- 账号回答“还能不能登录”。
- 自然人身份回答“这个账号是谁”。
- 校内关系回答“现在是不是在读学生/在职教职工”。
- 岗位回答“当前承担什么职责”。
- 角色绑定回答“本次会话可以做什么、管理哪里”。

任何一个状态变化都只能修改自己负责的层级，并通过统一生命周期服务计算下游影响。

### 3.2 撤权优先，删除最后

- 风险事件先撤销会话和业务权限，再异步处理通知、归档与交接。
- 不等待页面刷新，不依赖用户主动退出。
- 不通过删除账号来实现撤权。
- 已产生业务记录的人员原则上永不硬删除。

### 3.3 状态可恢复

休学、借调、安全冻结和销户冷静期都可能恢复。恢复必须重新计算当前有效身份和岗位，不能简单把历史角色全部改回 `active`。

### 3.4 历史责任不可改写

- 原教师发布的作业、评分和公告保留原操作者。
- 原辅导员的联系记录保留原记录人，但离岗后不能继续查看。
- 审批、任命和审计日志保留当时姓名、账号和岗位快照。
- 接任人获得后续处理权，不成为历史动作的执行人。

### 3.5 人事和学籍事件不由平台管理员随意决定

- 教务人员负责学籍事件。
- 学院负责人可以发起人员调岗和离岗建议。
- 正式环境应新增人事管理角色 `personnel_manager` 或接入人事主数据。
- 平台管理员只负责账号安全停用和平台权限，不应代替教务或人事决定学生/职工身份。

## 4. 状态模型

### 4.1 账号状态 `app_user.status`

| 状态 | 含义 | 登录能力 |
|---|---|---|
| `pending_approval` | 注册待审核 | 仅注册进度 |
| `active` | 正常账号 | 按有效工作身份登录 |
| `security_suspended` | 安全冻结 | 禁止业务登录，可走恢复流程 |
| `closure_pending` | 用户已申请销户、处于冷静期 | 仅销户状态/撤回入口 |
| `archived` | 已离校/离职，保留有限自助能力 | 仅按保留政策访问本人历史 |
| `closed` | 账号已完成销户 | 禁止普通登录 |
| `rejected` | 身份申请未通过 | 仅显示申请结果 |

登录失败锁定继续使用 `locked_until`，不再把临时密码锁定混入业务账号状态。

### 4.2 人员关系状态

新增 `person_affiliation`，避免一个字段同时承担自然人身份和当前在校/在职状态。

学生关系：

```text
pending -> active -> leave -> active
                  -> graduated
                  -> withdrawn
                  -> dismissed
```

教职工关系：

```text
pending -> active -> seconded/leave -> active
                  -> transferred
                  -> retired
                  -> terminated
```

`transferred` 表示一段组织关系结束，随后创建新的在职关系；不是自然人或账号被删除。

### 4.3 岗位和角色状态

继续使用现有模型：

- 岗位任职：`pending/active/suspended/ended/expired`。
- 角色绑定：`pending/active/suspended/revoked/expired`。

新增统一规则：

- 临时暂停使用 `suspended`，允许按原关系恢复。
- 永久结束使用 `ended/revoked`，恢复时创建新任期和新角色绑定，不复活旧历史记录。
- 角色有效还必须满足账号、人员关系和岗位任职同时有效。

### 4.4 基础自助身份

为已核验自然人建立无业务数据权限的 `self_service` 基础绑定，只允许：

- 个人资料和账号安全。
- 生命周期状态和处理进度。
- 销户申请与撤回。
- 按政策允许的本人历史记录或证明下载。

学生业务资格暂停后停用 `student` 绑定，但可保留 `self_service`；教职工结束全部岗位后也不必被迫成为无绑定异常账号。

## 5. 六类核心流程

### 5.1 单一岗位结束

适用：不再担任辅导员、负责人、审核员、教务或管理员，但人员仍在校任职。

```text
选择任职
→ 影响预览
→ 检查最后管理员/最低岗位覆盖
→ 选择直接结束或转任接替人
→ 结束 position_assignment
→ 撤销对应 user_role_binding
→ 释放/转移未完成任务
→ session_version + 1
→ 保留基础职工身份和其他岗位
```

当前 B.6 已完成大部分岗位操作；B.7 主要补充任务移交和最低覆盖联动。

### 5.2 跨学院或跨部门调动

适用：教职工仍在职，但组织归属和职责变化。

禁止直接修改 `staff.college_id` 后结束。必须使用一个原子化调岗流程：

1. 选择生效日期、新组织和新岗位。
2. 展示所有旧岗位、班级范围、审核任务和课程责任。
3. 指定每项责任的接任人或组织队列。
4. 生效时结束旧组织岗位和旧范围绑定。
5. 创建新的人员组织关系、岗位和范围绑定。
6. 递增会话版本，使所有旧范围令牌立即失效。
7. 记录调动前后组织快照，不覆盖历史任职。

未指定接任人的审核任务返回原组织队列；不能自动带到新学院。

### 5.3 学生休学与复学

休学生不是销户：

- `person_affiliation.status = leave`。
- 暂停新增选课、作业提交、课程问数等在读操作。
- `student` 角色绑定改为 `suspended`。
- 保留 `self_service`，允许查看休学状态、账号安全和政策允许的历史记录。
- 保留全部成绩、作业、考勤和支持记录。
- 旧会话立即失效。

复学时：

- 不恢复历史班级和课程权限快照。
- 根据复学后的学籍、班级和有效选课重新计算范围。
- 创建或重新激活新的学生业务绑定。
- 记录复学审批和生效日期。

### 5.4 学生毕业、退学或被取消学籍

| 事件 | 账号处理 | 学生业务权限 | 历史数据 |
|---|---|---|---|
| 毕业 | 转 `archived` 或校友自助状态 | 撤销新增教学操作 | 保留本人可查成绩/证明 |
| 主动退学 | 转 `archived` | 立即撤销 | 按学校政策保留 |
| 取消学籍 | 转 `archived`，必要时加安全限制 | 立即撤销 | 保留法定与审计记录 |

离校事件执行前必须处理：未完成课程、未提交成绩、未关闭申诉、未归还资料等阻塞项。阻塞项可以阻止“完成归档”，但不能阻止紧急撤权。

### 5.5 教职工离职、退休与返聘

离职执行顺序：

1. 人事事件进入待生效状态。
2. 生成全量影响报告。
3. 必须为正式岗位、授课班、审核任务、支持个案指定接任人或接收队列。
4. 到生效时间先撤销全部会话。
5. 结束全部岗位任职和岗位来源角色。
6. 结束或转交授课/辅导/审核责任。
7. `staff.employment_status` 与人员关系改为 `terminated/retired`。
8. 账号转 `archived`；关闭业务访问，按政策保留有限自助能力。
9. 保存审计及移交清单。

返聘不恢复旧岗位。重新激活人员关系后，通过新的任命产生新任期和新绑定。

### 5.6 用户主动销户

主动销户只关闭登录账号，不删除校内人员和历史业务事实。

```text
用户二次验证密码
→ 查看影响和数据保留说明
→ 检查是否仍有有效高权限岗位/待办
→ 提交销户申请
→ 立即撤销当前会话，账号 closure_pending
→ 7 天冷静期
→ 用户可重新验证身份后撤回
→ 到期后关闭凭据、撤销剩余非历史绑定，账号 closed
```

阻止直接销户的情况：

- 当前仍担任管理员、学院负责人、教务、辅导员、身份审核员等正式岗位。
- 是最后安全数量内的管理员。
- 仍领取未处理审核任务或需要移交的业务责任。
- 账号处于安全调查、申诉或法定保全状态。

学生或职工销户后重新使用系统，应走“账号恢复 + 身份重新核验”，不能用相同学号/工号创建第二个自然人账号。

## 6. 影响预览与任务移交

所有高影响事件必须先调用影响预览。报告至少包含：

- 将失效的角色和数据范围。
- 将失效的当前会话数量。
- 有效岗位和最低覆盖变化。
- 本人领取的注册/岗位审核任务。
- 辅导员未关闭支持个案和学生预约。
- 教师当前教学班、未评分作业和未发布成绩。
- 未完成的高风险审批。
- 需要通知的组织负责人。
- 是否允许立即执行、必须移交或只能预约生效。

任务处理原则：

- 注册/岗位审核任务返回其 `organization_review_queue`，不跟随个人调动。
- 辅导员个案按行政班的新有效辅导员重分配；没有接任人时进入学院异常队列。
- 教师课程责任必须由教务变更教学任务，不能由平台管理员直接“继承”。
- 历史动作保留原人员，只有未完成事项改变负责人。
- 转移与撤权在同一数据库事务中完成；通知可通过事务后事件异步发送。

## 7. 权限矩阵

| 操作者 | 可执行操作 | 明确禁止 |
|---|---|---|
| 本人 | 申请销户、冷静期撤回、查看本人状态 | 自行恢复业务身份、跳过岗位移交 |
| 辅导员 | 查看所带学生离校状态 | 修改学籍、关闭学生账号 |
| 教师 | 查看课程成员是否仍有课程资格 | 修改学籍或账号状态 |
| 学院负责人 | 结束/转移本学院岗位，发起职工调动/离岗建议 | 最终确认离职、跨学院自行扩权 |
| 身份审核员 | 身份重新核验、处理账号恢复申请 | 决定离职或毕业 |
| 教务人员 | 学生休学、复学、毕业、退学事件 | 管理职工人事状态、授予管理员 |
| 人事管理员 `personnel_manager` | 职工调动、离职、退休、返聘 | 查看不必要的教学隐私 |
| 平台管理员 | 安全停用/恢复账号、执行已批准撤权、平台岗位保护 | 决定学籍或人事事实、删除历史数据 |
| 系统同步账号 | 根据权威主数据提交幂等生命周期事件 | 直接绕过冲突与异常队列 |

在尚未接入人事角色的演示阶段，可由两名具名管理员共同确认职工离职事件，但页面必须标注为临时替代流程，不能把平台管理员永久设计成人事部门。

## 8. 数据设计

### 8.1 `person_affiliation`

| 字段 | 说明 |
|---|---|
| `id` | 校内关系 ID |
| `person_identity_id` | 自然人 |
| `affiliation_type` | `student/staff` |
| `source_entity_id` | 学生或职工主数据 ID |
| `organization_unit_id` | 当前组织 |
| `status` | 在读/在职及离校/离职状态 |
| `valid_from/valid_until` | 关系有效期 |
| `source_system` | 手工、教务、人事或统一身份源 |
| `source_event_id` | 幂等事件标识 |

### 8.2 `identity_lifecycle_event`

| 字段 | 说明 |
|---|---|
| `event_type` | 休学、复学、毕业、调动、离职、退休、返聘等 |
| `target_user_id/person_identity_id` | 影响对象 |
| `status` | `draft/pending_approval/approved/scheduled/executing/completed/failed/canceled` |
| `effective_at` | 生效时间 |
| `reason/evidence` | 原因和依据 |
| `requested_by/approved_by/executed_by` | 全链路责任人 |
| `idempotency_key` | 防止外部同步重复执行 |
| `before_snapshot/after_snapshot` | 状态快照 |
| `impact_snapshot` | 执行时确认过的影响 |

### 8.3 `account_closure_request`

记录申请、冷静期截止、二次验证、阻塞原因、撤回、完成时间和最终处理人。密码、验证码和恢复令牌只保存哈希，不写审计明文。

### 8.4 `responsibility_handover`

记录原负责人、接任人/队列、资源类型、资源 ID、交接状态和确认时间。生命周期事件只有在必须交接项全部完成或已进入异常队列后才能标记完成。

### 8.5 `account_status_history`

账号每次状态变化都记录前后状态、来源事件、操作者、原因、时间和会话版本，不能只覆盖 `app_user.status`。

## 9. 接口方案

### 9.1 管理侧

```text
GET  /api/lifecycle/people/{person_identity_id}
GET  /api/lifecycle/people/{person_identity_id}/impact?event_type=...
POST /api/lifecycle/events
GET  /api/lifecycle/events
GET  /api/lifecycle/events/{event_id}
POST /api/lifecycle/events/{event_id}/approve
POST /api/lifecycle/events/{event_id}/cancel
POST /api/lifecycle/events/{event_id}/execute
POST /api/lifecycle/events/{event_id}/retry
POST /api/lifecycle/handovers/{handover_id}/assign
POST /api/lifecycle/handovers/{handover_id}/confirm
```

### 9.2 本人账号侧

```text
GET  /api/auth/lifecycle
POST /api/auth/closure/impact
POST /api/auth/closure/request
POST /api/auth/closure/cancel
POST /api/auth/reactivation/request
```

### 9.3 外部同步

```text
POST /api/internal/lifecycle-events
GET  /api/internal/lifecycle-events/{idempotency_key}
```

外部接口必须使用服务身份、签名、幂等键和来源白名单，不能复用普通管理员令牌。

## 10. 页面方案

### 10.1 人员生命周期详情

从组织人员目录进入，不恢复“全校账号密码列表”。页面包括：

- 当前账号状态、学籍/任职状态。
- 当前岗位、角色和范围。
- 状态时间线。
- 未完成责任和交接项。
- 影响预览。
- 当前操作者有权执行的事件按钮。

按钮使用明确业务语言，例如“办理休学”“结束任职”“发起调岗”“办理离职”“安全停用”，不使用含义模糊的统一“注销”。

### 10.2 本人账号安全页

- 展示账号状态和当前有效身份。
- 提供主动销户、销户进度和冷静期撤回。
- 在提交前明确说明保留哪些业务记录、何时停止登录、如何恢复。
- 有岗位阻塞时直接链接到需要联系的组织和未移交事项。

### 10.3 生命周期待办中心

- 待审批事件。
- 今日/未来生效事件。
- 执行失败和数据冲突。
- 未完成交接。
- 无接任人的组织异常。
- 外部主数据与本地状态不一致。

## 11. 安全、审计与数据保留

- 所有状态改变都使 `session_version + 1`。
- 高权限账号停用、离职和销户要求二次验证，且受最后管理员保护。
- 执行前后写不可篡改审计，记录事件、影响、移交和结果。
- 不在日志中记录密码、验证码、完整身份证件或恢复令牌。
- 关闭账号时将密码替换为不可登录随机哈希，清除恢复凭据和活动会话。
- 业务记录使用稳定人员 ID；显示层可以根据保留政策脱敏，但不得破坏外键和审计链。
- 只有从未通过身份审核、没有任何业务记录的错误账号，才允许经过审批后物理清理。
- 法定保全、申诉或安全调查期间禁止最终销户和匿名化。
- 批量毕业/离职逐项校验；一条失败不能导致已完成对象回滚，也不能跳过失败对象继续伪报全批成功。

## 12. 异常与恢复

### 12.1 事件重复

相同 `idempotency_key` 返回原结果，不重复撤权或创建新任期。

### 12.2 执行中断

账号撤权、绑定变更和关键交接在一个事务内完成。事务失败保持旧状态；异步通知失败进入重试，不回滚已经完成的安全撤权。

### 12.3 错误停用

通过反向事件恢复账号，但重新计算现有身份和岗位。已经结束的历史任职不直接改回 `active`。

### 12.4 无接任人

紧急离职可以先撤权，未完成责任进入组织异常队列；非紧急预约离职必须先完成必需交接。

### 12.5 同一人再次入校/入职

优先恢复同一 `person_identity` 和账号，新增一段 `person_affiliation`。只有确认是不同自然人时才允许相同显示姓名产生新人员记录，学号/工号是否复用由权威主数据规则决定。

## 13. 开发阶段

### B.7-0：状态模型与影响预览

**状态：已完成（2026-07-17）。**

- 新增人员关系、生命周期事件、状态历史和交接表。
- 增加 `self_service` 基础绑定。
- 实现统一影响计算器和只读预览接口。

实施结果：

- 已建立 `person_affiliation`、`identity_lifecycle_event`、`account_closure_request`、`responsibility_handover` 和 `account_status_history`。
- 已为真实演示库 23 个已核验人员建立 23 条关系基线、23 个隐藏基础自助绑定和 23 条初始账号状态历史。
- `self_service` 不干扰正常角色选择；业务角色全部暂停后可作为只有个人中心权限的安全入口。
- 已实现本人及权限范围内人员详情，以及休学、复学、毕业、退学、调岗、离职、退休、安全停用和主动销户的只读影响预览。
- 影响报告包含角色、岗位、会话、审核任务、课程/支持责任、最低覆盖阻塞、警告和交接要求。
- 当前明确不提供执行接口，影响响应返回 `execution_available = false`。
- 完整自动化测试 108 项通过。

验收：任何离校、离职、调岗和销户事件都能在不修改数据的情况下列出权限、会话、岗位和待办影响。

### B.7-1：账号安全停用与恢复

**状态：已完成（2026-07-17）。**

- 管理员安全冻结/恢复。
- 会话立即失效。
- 高权限保护、二次验证和审计。

实施结果：

- 提供 `POST /api/lifecycle/people/{person_identity_id}/security-suspend` 与 `security-restore`，仅当前有效的平台管理员可操作。
- 每次冻结和恢复都会递增 `session_version`，旧令牌立即失效；冻结账号不能重新登录或签发新令牌。
- 操作必须填写依据并验证当前管理员密码；失败的二次验证、尝试冻结自身和正式平台管理员保底拦截都会留下安全审计。
- 冻结只改变 `app_user.status`，不会删除人员、岗位或角色绑定；恢复仅将账号恢复为 `active`，因此冻结期间已撤销、到期或结束的岗位/角色不会被复活。
- 每次迁移均写入 `identity_lifecycle_event`、`account_status_history` 和 `audit_log`；组织教职工目录为平台管理员提供最小化的冻结/恢复入口。

验收：被冻结账号不能使用旧令牌；恢复后只获得当前仍有效的身份，不恢复已撤销岗位。

### B.7-2：学生生命周期

**状态：已完成（2026-07-17）。**

- 休学、复学、毕业、退学流程。
- 学生业务绑定暂停/撤销。
- 历史数据只读和批量毕业。

实施结果：

- 仅教务处工作身份可办理学生休学、复学、毕业、退学；平台管理员不能替代教务决定学籍事实。
- 休学将 `student.status` 与当前学生关系改为 `leave`，暂停学生业务绑定并递增会话版本；账号保留 `self_service` 最低权限入口。
- 复学根据当前学籍重新建立一条有效学生绑定和关系记录，不反向启用历史学生绑定或恢复旧会话。
- 毕业/退学将学生业务绑定撤销，账号归档为 `archived`，所有旧令牌和新登录均失效；成绩、作业、考勤、选课和支持记录均保留在原数据中。
- 提供单人办理、学生清单和最多 500 人的批量毕业接口；批量操作会先校验全体对象，避免出现部分完成。
- 每次操作记录生命周期事件、必要的账号状态历史和学生生命周期审计；教务处可在组织与岗位页面使用最小化管理入口。

验收：休学学生不能提交新作业但能查看允许的本人状态；复学按当前班级重算；毕业不删除成绩。

### B.7-3：职工调岗、离职和退休

**状态：已完成（2026-07-17）。**

- 新增人事管理员或双人临时审批。
- 跨组织原子调岗。
- 全岗位/课程/队列/个案交接。

实施结果：

- 在尚未引入独立 `personnel_manager` 的演示阶段，采用两名不同具名平台管理员的临时双确认流程；同一管理员不能同时发起和确认。
- 跨学院调动会关闭旧人员关系、建立新学院关系、结束全部旧岗位和业务角色并递增会话版本；不会自动授予目标学院的新岗位或数据范围。
- 离职/退休会结束全部岗位、撤销除基础自助绑定外的业务角色、归档账号并撤销会话。
- 已领取审核任务会原子返回原组织审核队列；当前教学班和未关闭辅导个案会生成明确的交接/异常清单，保留原业务责任和历史记录，等待教务或学院指定接任人。
- 变动记录写入生命周期事件、账号状态历史（账号归档时）、责任交接和审计日志。

验收：旧学院令牌立即失效，未完成任务不丢失，返聘不复活旧任期。

### B.7-4：主动销户

- 销户影响、二次验证、冷静期、撤回和完成。
- 凭据销毁、账号恢复申请和阻塞规则。

验收：有正式岗位的人员不能直接销户；普通用户完成销户后旧令牌失效且历史记录完整。

### B.7-5：外部同步与完整回归

## 14. 核心验收用例

1. 辅导员结束岗位后保留教师身份，但不能再查看原行政班支持记录。
2. 学院负责人跨学院调动后旧学院权限立即失效，不自动获得新学院负责人权限。
3. 学生休学后旧令牌失效，不能提交作业；复学后只获得当前有效课程。
4. 学生毕业后成绩和作业历史仍在，不能执行在读操作。
5. 职工离职结束全部岗位，领取的审核任务返回组织队列。
6. 辅导员离职后未关闭个案转给接任辅导员或学院异常队列。
7. 教师离职不改写历史评分人，未完成教学责任必须由教务交接。
8. 销户申请进入冷静期并立即撤销业务会话，冷静期内可以安全撤回。
9. 最后安全数量内的管理员不能离职、结束岗位或销户，除非先完成接任。
10. 修改 `student.status` 或 `staff.employment_status` 的单个字段不能绕过生命周期服务形成半撤权状态。
11. 同一外部离职事件重复发送只执行一次。
12. 生命周期执行失败有明确重试/人工处理入口，不产生部分角色仍有效的状态。

## 15. 与后续阶段的关系

建议把本方案作为 **B.7**，在通知中心和课程空间阶段前至少完成 B.7-0 至 B.7-3。原因是通知、课程责任、审核任务和学生支持一旦继续扩展，离职/离校时需要移交的对象会更多；先建立统一生命周期事件和交接机制，可以避免每个新模块各自实现一套不一致的“注销”。
